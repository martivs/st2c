# Как вести работу по плану: инструкция человеку

Спутник `PLAN-2026-08-07.md`. Там — что делать модели, здесь — что делать тебе.

Работа разбита на **восемь этапов, по одной сессии на каждый**. Открываешь
новую сессию, даёшь готовый промпт из этого файла, принимаешь результат,
закрываешь. Промпты ниже самодостаточны: их можно копировать не читая ничего
вокруг.

**Важно про `examples/`.** Там семь файлов, и три из них (`func_simple.st`,
`fb_counter.st`, `fb_nested.st`) до этапа 3b честно падают с
`expected PROGRAM at top level` — они написаны заранее как приёмочная цель.
Это **не поломка**. Таблица «Готовность примеров по этапам» — в
`PLAN-2026-08-07.md`; на каждом этапе прогоняй ровно те, что уже должны
работать.

---

## Почему одна сессия на этап

Модель держит в голове ограниченный объём контекста. Чем длиннее сессия, тем
больше в ней накапливается: прочитанные файлы, отвергнутые варианты, следы
ошибок. К какому-то моменту важное вытесняется мусором — модель начинает
забывать принятые решения, переделывать уже сделанное, спорить сама с собой.

Лечится это не уговорами, а перезапуском. Новая сессия читает `CLAUDE.md` и
`PLAN-2026-08-07.md` — два коротких документа вместо всей истории — и стартует
с чистой головой, зная ровно то, что нужно.

**Отсюда единственное правило, которое нельзя нарушать: `CLAUDE.md`
обновляется в том же коммите, что и код.** Не «потом», не «в конце». Если
этап закрыт, а `CLAUDE.md` не тронут — следующая сессия начнёт с нуля и
переоткроет уже решённые вопросы. Проверять это глазами после каждого этапа —
твоя главная работа в этой схеме.

---

## Перед каждой сессией

```bash
cd ~/projects/work/st2c
git status              # должно быть чисто
git branch --show-current   # develop
go build ./... && go vet ./... && go test ./...   # всё чисто и зелено
```

Если что-то из этого не так — сначала разберись, потом начинай этап. Модель,
стартующая на грязном дереве, потратит полсессии на выяснение, чьи это правки.

**Модель.** Команда `/model` в начале сессии. Для Fable 5:

```
/model fable
```

**Plan mode.** Для крупных этапов (1, 4, 6, 7) стоит включить: модель сначала
покажет план, ты его посмотришь и дашь добро, и только потом она начнёт
править файлы. Для этапов 1, 2, 5 не обязательно — они узкие. Переключение
режима — Shift+Tab (циклически: обычный → auto-accept → plan) либо через
переключатель режима в интерфейсе.

Оговорка честности: конкретных поведенческих особенностей Fable 5 в этой
инструкции нет — я их не проверял и выдумывать не буду. Всё написанное здесь
про механику Claude Code, которая от выбранной модели не зависит.

## После каждой сессии

Приёмка занимает пару минут и стоит того.

```bash
go build ./... && go vet ./... && go test ./...

# для этапов 1, 2, 5, 7 — собрать и запустить C руками:
go run ./src -main -o /tmp/a.c examples/example.st && gcc /tmp/a.c -o /tmp/a && /tmp/a

git show --stat            # что вообще поменялось
git show -- CLAUDE.md      # ← самое важное
```

**Diff `CLAUDE.md` читать глазами всегда.** Это единственная гарантия, что
следующая сессия не начнёт с чистого листа. Если правок в нём нет или они
косметические — этап не закрыт, верни модель дописывать. Если решения из
плана переехали туда с искажениями — поправь сейчас, через два этапа будет
дороже.

Дальше — `git log --oneline -1` и проверка, что коммит один и осмысленный.

## Если сессия «поплыла»

Признаки, что контекст переполнился:

- модель повторяет то, что уже говорила несколькими сообщениями раньше;
- забывает решения из плана и предлагает переоткрыть их заново;
- правит код, который уже поправила в этой же сессии;
- отвечает всё более общо, перестаёт ссылаться на конкретные файлы и строки.

Что делать:

1. Прервать (Esc).
2. Если есть рабочее промежуточное состояние — попросить закоммитить его
   отдельно, с честным сообщением о том, что этап не закончен.
3. `/clear` или новая сессия.
4. Начать этап заново тем же промптом, добавив строку: «Этап начат в
   предыдущей сессии, часть работы уже в коммите <хеш> — посмотри `git log` и
   `git show`, продолжи с этого места».

Если этап не влезает в сессию дважды подряд — он слишком крупный. Разрежь его
пополам прямо в `PLAN-2026-08-07.md` и веди дальше как два, с буквенными
номерами. Так уже сделано с этапом 3 (был один на три пакета, стал 3a
«лексер + AST» и 3b «парсер»): нумерацию менять не пришлось, а сессии стали
подъёмными. По тем же швам делится этап 4 (таблица POU / проверки вызовов) и
этап 7 (typedef и _init / разворот вызова). План для этого и лежит в
репозитории — он рабочий документ, а не памятник.

## Что не надо делать

- **Не веди два этапа в одной сессии**, даже если первый закончился быстро.
  Экономия в пятнадцать минут стоит потом часа на разбор перепутанного
  коммита.
- **Не пропускай обновление `CLAUDE.md`** «потому что этап маленький». Именно
  на маленьких этапах это и пропускают, а потери накапливаются.
- **Не принимай перегенерацию golden-эталонов не глядя.** Структура дерева
  (приоритеты операций, ассоциативность) и текст сгенерированного C не должны
  меняться незаметно — это правило было в проекте с самого начала и с приходом
  `*.c`-эталонов стало важнее, а не слабее.
- **Не позволяй расширять типы.** `BOOL`, `REAL`, массивы — за рамками этой
  работы. Если модель предлагает «заодно добавить», отвечай «нет, по плану».
