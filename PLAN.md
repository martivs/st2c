# План: закрытие долгов фронтенда st2c до Этапа 3 (codegen)

> **Как пользоваться этим файлом.** Это источник правды для исполнения. Работа
> разбита на 3 подзадачи (см. раздел «Исполнение»), каждая запускается **отдельной
> свежей сессией** по своему триггер-промпту и завершается отчётом в
> `REVIEW-2026-07-09.md`. Диагностика проблем и обоснования — в
> `REVIEW-2026-07-09.md`; текущее состояние кода — в `CLAUDE.md` и `src/`.

## Контекст

Этап 2 завершён (лексер, парсер, AST — рабочие, `example.st` разбирается). Ревью
`REVIEW-2026-07-09.md` вскрыло 5 подтверждённых запуском багов и ряд
архитектурных решений, которые дёшево поправить сейчас и дорого — после того как
codegen на них завяжется. Цель этого плана: **не переходя к codegen (Этап 3),
закрыть максимум того, что иначе создаст боль при масштабировании транслятора до
полного ST** (все типы, функции, функциональные блоки).

Принцип отбора: в план входит то, что (а) ломает реальные ST-файлы, либо (б)
меняет *формы данных*, на которые завяжется будущий код, либо (в) убирает
структурное дублирование, растущее с каждым новым типом/оператором. То, что
позже добавляется дёшево и локально (новые операторы управления, богатые
литералы, восстановление после ошибок), вынесено в раздел «Отложено» с
обоснованием.

Работа разбита на **7 независимо проверяемых фаз**. Каждая фаза = отдельный
коммит: `go build ./...` и `go vet ./...` чисто, `go test ./...` зелено. Фаза 0
(тесты) идёт первой намеренно — она страховочная сетка для рефакторингов фаз 2,
4, 5. После каждой фазы обновляется `CLAUDE.md` (таблица статусов, список файлов)
и отмечается закрытый пункт ревью.

**Что НЕ делаем:** саму кодогенерацию; раскладку каталогов `src/` → `internal/`
(косметика, боли при масштабировании не создаёт — отдельный механический коммит
когда/если появится CI).

## Фаза 0 — Тестовая инфраструктура (страховочная сетка)

**Зачем первой:** дальше идут рефакторинги, меняющие форму AST (Pratt, `ast.Op`,
lvalue, VAR-блоки, SourceFile). Без golden-тестов регрессии в приоритете
операций и структуре дерева пройдут незамеченными.

**Файлы (новые):**
- `src/lexer/lexer_test.go` — table-driven: вход-строка → ожидаемый список
  `(Type, Literal)`. Покрыть все текущие токены.
- `src/parser/parser_test.go` — golden: читает `testdata/*.st`, сравнивает
  `prog.String()` с `testdata/*.ast`. Плюс тесты ошибок: вход → подстрока
  ожидаемого сообщения (с номером строки).
- `src/parser/testdata/` — 4 существующих примера (`example`, `nested_if_in_for`,
  `nested_for_in_if`, `deeply_nested`) + сгенерированные `.ast`-эталоны.

**Дисциплина golden:** эталоны генерируются флагом (`go test -run X -update`) и
коммитятся; при осознанном изменении формата `String()` эталоны
перегенерируются, а diff просматривается вручную.

**Готово когда:** `go test ./...` зелено, эталоны совпадают с текущим выводом.

## Фаза 1 — Устойчивость лексера (баги 1.1, 1.3, 1.4 + долги L1, L3, L6)

Все правки лексер-локальные, дерево не трогают.

**Файл:** `src/lexer/lexer.go` (+ тесты).

1. **Комментарии (баг 1.1):** `(* ... *)` (с поддержкой вложенности) и `// ...`
   до конца строки. Хук в `NextToken`: `(` + `peek()=='*'` → блочный;
   `/` + `peek()=='/'` → строчный. Одиночные `(` и `/` остаются `LPAREN`/`SLASH`.
   Внутри блочного комментария инкрементировать `line`.
2. **Двухсимвольные операторы (баг 1.3):** `<=`→`LE`, `>=`→`GE`, `<>`→`NE` по
   образцу существующего `:=`. Добавить типы `LE, GE, NE` + записи в `tokenNames`.
3. **Ключевое слово `BY` (баг 1.4):** добавить в `keywords` (само поле шага —
   в фазе 3).
4. **Долг L3 (тройное дублирование):** `tokenNames` для ключевых слов строить из
   `keywords` в `init()`. Снять TODO на строке 100.
5. **Долг L1 (позиция):** добавить `Col int` в `Token`, вести колонку в `Lexer`
   (сброс на `\n`). Ретрофит позиций позже задел бы каждый узел — дешевле сейчас.
6. **Долг L6:** снять FIXME в `skipWhitespace` (текущая обработка `\n`/`\r`
   корректна для LF и CRLF — зафиксировать комментарием).

**Готово когда:** тесты на комментарии, `<= >= <>`, `BY`, колонки — зелёные;
golden-эталоны фазы 0 не изменились (кроме добавленных токенов).

## Фаза 2 — Фундамент выражений: унарный минус + Pratt + `ast.Op` (баг 1.2, долги P1, A1)

**Единственный «крупный» рефактор**, поэтому идёт под защитой фазы 0.

**Файлы:** `src/ast/ast.go`, `src/parser/parser.go` (+ тесты).

1. **`ast.Op` (долг A1):** собственный enum операций (`ADD, SUB, MUL, DIV, LT, LE,
   GT, GE, EQ, NE, NEG, …`) с методом `String()`, возвращающим те же символы
   (`+`, `-`, `<=`), чтобы golden-эталоны остались текстово стабильными.
   `BinaryExpr.Op` меняет тип с `lexer.TokenType` на `ast.Op`. Отвязывает AST от
   представления токенов — важно для будущей семантики/оптимизаций.
2. **Унарный минус (баг 1.2):** узел `ast.UnaryExpr{Op, Operand}`; в грамматике —
   уровень `parseUnary` (обрабатывает `-` и на будущее унарный `+`, `NOT`).
3. **Pratt-переход (долг P1):** каскад `parseExpression/parseAdditive/
   parseMultiplicative` заменить на одну `parseExpression(minPrec int)` +
   таблицу `prec map[lexer.TokenType]int`. `parsePrimary` и левая
   ассоциативность сохраняются. Новый оператор в будущем = одна строка в таблице.

**Критичная проверка:** после рефактора структура дерева (приоритеты,
ассоциативность) должна совпасть с фазой 0 — golden-diff показывает только
осознанные изменения. Добавить тесты: `a - b - c` (левая ассоц.), `a + b * c`
(приоритет), `-x + 1`, `a <= b`, `(i + j) > 4`.

**Готово когда:** golden-эталоны совпадают (после осознанной перегенерации, если
менялись метки), новые тесты приоритетов зелёные.

## Фаза 3 — Присваивание как lvalue + `FOR ... BY` (долг P2, баг 1.4)

Меняет форму данных, на которую завяжется codegen, — поэтому до него.

**Файлы:** `src/ast/ast.go`, `src/parser/parser.go` (+ тесты).

1. **`AssignStatement.Target`: `string` → `Expression` (долг P2).** Сейчас цель —
   голая строка; сломается на первом `arr[i] :=`, `fb.out :=`. `parseAssign`
   начинает с разбора primary (lvalue), затем ждёт `ASSIGN`. Пока допустимый
   lvalue — только `Identifier` (литерал слева → ошибка), но узлы `IndexExpr`/
   `MemberExpr` добавятся сюда же позже без смены формы. Обновить `String()`.
2. **`FOR ... BY step` (баг 1.4):** `ForStatement.Step Expression` (nil → шаг 1);
   `parseFor` читает необязательный `BY` перед `DO`. `ForStatement.Var` оставить
   простым идентификатором (по IEC переменная цикла — простая), но хранить как
   `*Identifier` ради позиции. Обновить `String()`.

**Готово когда:** тесты `FOR i:=1 TO 10 BY 2 DO`, отклонение `5 := x`, позиция в
ошибке присваивания — зелёные.

## Фаза 4 — Фундамент объявлений: тип-как-данные + виды VAR-блоков (долги P3, P4, L5)

Прямо снимает риск для функций/FB — их интерфейс задаётся именно видами блоков.

**Файлы:** `src/lexer/lexer.go`, `src/ast/ast.go`, `src/parser/parser.go` (+ тесты).

1. **Тип в объявлении (долг P3, L5):** `VarDecl` получает `TypeName string`
   (пока строка-имя типа), список имён `Names []string` (`a, b, c : INT;`) и
   необязательный инициализатор `Init Expression` (`x : INT := 5;`). Парсер
   перестаёт хардкодить `p.expect(lexer.INT)` — `parseType()` принимает и
   ключевое слово `INT`, и любой `IDENT` (пользовательские типы не должны падать;
   ограничение допустимых типов — задача sema, фаза 6). `INT` в `String()` больше
   не константа, а `TypeName`.
2. **Виды блоков (долг P4):** `Program.Vars` → `Program.VarBlocks []*VarBlock`,
   где `VarBlock{Kind VarKind, Decls []*VarDecl}`. Добавить в лексер ключевые
   слова `VAR_INPUT, VAR_OUTPUT, VAR_IN_OUT, VAR_TEMP, CONSTANT` (плюс `RETAIN`
   по желанию). `parseVarBlocks` — цикл по всему семейству `VAR*`.

**Готово когда:** тесты на несколько блоков, список имён, инициализатор,
пользовательское имя типа — зелёные; существующие примеры (один `VAR`-блок с
`INT`) разбираются как прежде.

## Фаза 5 — Структура компилируемой единицы: SourceFile / каркас POU (долг P5)

Снимает риск для добавления `FUNCTION`/`FUNCTION_BLOCK` позже — корень дерева
перестаёт быть жёстко «одна PROGRAM».

**Файлы:** `src/ast/ast.go`, `src/parser/parser.go`, `src/main.go` (+ тесты).

1. **`ast.SourceFile{POUs []POU}`** как новый корень; интерфейс `POU`; `Program`
   реализует `POU`. `main.go` печатает каждый POU.
2. **`ParseSourceFile`** — цикл по POU до EOF. Диспетчер по стартовому ключевому
   слову; пока распознаётся только `PROGRAM`, но `switch` структурирован так,
   что `FUNCTION`/`FUNCTION_BLOCK` — это будущая ветка (тела не парсим сейчас,
   см. «Отложено»).

**Готово когда:** существующие одно-`PROGRAM` файлы разбираются через новый
корень без изменения вывода; тест на цикл POU (один PROGRAM) зелёный.

## Фаза 6 — Семантический анализ: пакет `sema` (раздел 2.5 ревью + баг 1.5)

Закрывает молчаливые ошибки, из-за которых сгенерированный C был бы некорректен.
Ставится между парсером и (будущим) codegen, чтобы проверки не осели в codegen.

**Файлы (новые):** `src/sema/sema.go` (+ тесты); правка `src/main.go`.

- `Check(*ast.SourceFile) []error`. Символьная таблица `map[string]*Symbol` с
  ключом `strings.ToUpper(name)` — **регистронезависимость идентификаторов**
  (по IEC `Sum` и `sum` — одна переменная; сейчас это молча расходится).
- Проверки: объявленность (ссылки, цели присваивания, переменная `FOR`);
  дубликаты объявлений; **диапазон `INT` −32768..32767 для литералов (баг 1.5)**
  при известном целевом типе. Все ошибки — с номером строки/колонки.
- `main.go`: после парсинга запускать sema, печатать все ошибки, выходить с
  ненулевым кодом.

Один уровень области видимости сейчас; стек scope-ов появится с функциями.
Полный **вывод типов выражений и неявные преобразования** — отложены (нужен
codegen для сквозной проверки, см. ниже); сейчас достаточно диапазона и
объявленности.

**Готово когда:** тесты на необъявленную переменную, `Sum`/`sum`, дубль
объявления, `x : INT := 100000` (вне диапазона) — зелёные.

## Отложено (дешевле после появления codegen — сознательно НЕ в этом плане)

| Пункт ревью | Почему можно потом малой кровью |
|---|---|
| Тела `FUNCTION` / `FUNCTION_BLOCK` (P-часть 6 ревью) | Каркас `SourceFile`/`POU` (фаза 5) и виды VAR-блоков (фаза 4) — структурный риск — уже сняты. Сам разбор тел добавляется как новая ветка `switch`, не меняя существующие формы. Осмысленно делать вместе с их codegen (FB → struct + функция), иначе не проверить сквозным C. |
| Операторы `ELSIF / WHILE / REPEAT / CASE / EXIT / RETURN` (P7) | Встают в `parseStatement` и `isBlockEnd` независимо, структурного долга не создают. Добавлять инкрементально, можно даже после codegen. |
| Полный вывод типов + неявные/явные преобразования (Этап 4 ревью, A4) | Требует рабочего codegen для сквозной проверки корректности C. Поле `TypeName` (фаза 4) — задел; вывод типов — отдельный слой в sema позже (side-table `map[Expression]Type`). |
| Богатые литералы: `16#FF`, `2#1010`, `1_000`, `3.14`, `T#1s`, строки (L4, L7) | Лексер-локальны, добавляются с типами, которым нужны (`REAL`/`STRING`/`TIME`). Не блокируют INT-фундамент. |
| Восстановление после ошибок / много ошибок за проход (P6) | Не структурно: поле `err` расширяется до `errs []error` без переделки. Качество жизни, не масштабирование. |
| Вызовы функций в выражениях `f(x)` (P9) | При Pratt (фаза 2) `(` после primary — постфиксный оператор; ляжет в ту же таблицу, когда появятся функции. |
| Раскладка `src/` → `internal/` + `cmd/` (M4) | Косметика, внешних импортов нет. Отдельный механический коммит при появлении CI. |
| CLI `-o out.c` (M3) | Нужен только для codegen. Полезные сейчас `-dump-ast` / `-dump-tokens` можно добавить попутно в фазе 5/6 при правке `main.go`. |

## Исполнение: 3 самостоятельных наряда

План разбит на **3 последовательные подзадачи-наряда**. Каждый исполняется
**отдельной сессией** и завершается записью отчёта в `REVIEW-2026-07-09.md`.
Порядок строгий: 1 → 2 → 3 (каждая опирается на зелёную предыдущую).

### Как запускать (механика)

1. **Сменить модель** (по желанию): `/model <модель>` — например `fable`.
2. **Запустить наряд**: вставить триггер-промпт подзадачи (ниже) новой сессией.
   Это и есть «нажать, чтобы задача выполнилась».
3. Сессия делает работу, прогоняет проверки и **последним шагом дописывает
   отчёт** в `REVIEW-2026-07-09.md` (формат — ниже).
4. Проверить отчёт и зелёные тесты → перейти к следующему наряду.

### Формат отчётности (в конце КАЖДОГО наряда, в `REVIEW-2026-07-09.md`)

Исполнитель обязан, как финальный шаг:
- В теле ревью пометить закрытые пункты префиксом `✅ [закрыто пN]` (N — номер
  подзадачи), не удаляя текст.
- В конце файла в раздел `## Журнал выполнения` (создать, если нет) добавить блок:
  ```
  ### Подзадача N — <название> — <дата>, модель <model>
  - Закрытые пункты ревью: <напр. 1.1, 1.3, 1.4, L1, L3, L6>
  - Изменённые/новые файлы: <список>
  - Проверки: go build/vet ./... — ок; go test ./... — <N passed>;
    ручные прогоны — <что проверено>
  - Заметки/что осталось: <нюансы, отложенное>
  ```

### Подзадача 1 — «Сетка + лексер» (фазы 0–1)
- **Риск: минимальный.** Формы AST не трогаются: только новые тесты и
  лексер-локальные правки. Роль — страховочная сетка для подзадач 2–3.
- **Готово когда:** `go build/vet/test ./...` чисто и зелено; golden-эталоны
  зафиксированы; негативные прогоны по комментариям, `<= >= <>`, `BY` проходят.
- **Триггер-промпт:**
  > Выполни Подзадачу 1 (фазы 0–1) из плана `PLAN.md` в корне репозитория.
  > Сначала прочитай `PLAN.md`, `REVIEW-2026-07-09.md`, `CLAUDE.md` и код в
  > `src/`. Не выходи за рамки подзадачи. Финальным шагом внеси отчёт в
  > `REVIEW-2026-07-09.md` по формату из раздела «Формат отчётности» плана.

### Подзадача 2 — «Фундамент выражений и присваивания» (фазы 2–3)
- **Риск: наивысший** (Pratt-рефактор + `BinaryExpr.Op` → `ast.Op` +
  `AssignStatement.Target` → `Expression`). Изолирован намеренно, целиком под
  golden-тестами подзадачи 1.
- **Предупреждение исполнителю:** golden `.ast` **перегенерируются** (метки `Op`,
  форма присваивания) — это ожидаемо; diff просмотреть вручную, структура дерева
  (приоритеты/ассоциативность) обязана сохраниться.
- **Готово когда:** тесты приоритетов/ассоциативности зелёные; 4 примера дают ту
  же структуру дерева, что и до рефактора.
- **Триггер-промпт:**
  > Выполни Подзадачу 2 (фазы 2–3) из плана `PLAN.md` в корне репозитория.
  > Сначала прочитай `PLAN.md`, `REVIEW-2026-07-09.md`, `CLAUDE.md` и код в
  > `src/`. Предыдущая подзадача завершена. Не выходи за рамки подзадачи.
  > Финальным шагом внеси отчёт в `REVIEW-2026-07-09.md` по формату из раздела
  > «Формат отчётности».

### Подзадача 3 — «Объявления, единицы, семантика» (фазы 4–6)
- **Риск: средний.** Фазы связные и нарастают: тип-как-данные → виды VAR-блоков →
  SourceFile/POU → sema. Меняют формы объявлений и корень дерева.
- **Готово когда:** несколько VAR-блоков/списки имён/инициализаторы разбираются;
  корень — SourceFile; sema ловит необъявленные, регистр (`Sum`=`sum`), дубли,
  диапазон INT.
- Если объёмно для одной сессии — под-шов: сначала фазы 4+5 (структура), затем

## Порядок и зависимости

`0 (тесты)` → `1 (лексер)` → `2 (выражения/Pratt)` → `3 (lvalue/FOR BY)` →
`4 (объявления/типы/VAR-блоки)` → `5 (SourceFile/POU)` → `6 (sema)`.

Фазы 3–6 опираются на страховку фазы 0 и на `ast.Op`/Pratt из фазы 2. Внутри
фазы 4 сначала `VarDecl.TypeName`, потом `VarBlock` (второе использует первое).
Каждая фаза самодостаточна и коммитится отдельно.
