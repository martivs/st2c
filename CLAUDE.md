# ST → C Transpiler

Транспилятор: ST (Structured Text, IEC 61131-3) → C. Язык реализации: Go,
только стандартная библиотека. Модуль `st2c`, go 1.22.

Этот файл — **единственный постоянный документ проекта** и источник контекста
для новых сессий: состояние, принятые решения, дорожная карта, долги. Планы
работ — временные черновики и после завершения удаляются, существенное
переезжает сюда. История доработок фронтенда (`PLAN.md`,
`REVIEW-2026-07-09.md`) — в коммитах до 2026-07-19; план 2026-08-07
(8 этапов: codegen + FUNCTION + FUNCTION_BLOCK, файлы `PLAN-2026-08-07.md` и
`SESSIONS-2026-08-07.md`) завершён и удалён коммитом 0.1.0 от 2026-08-09.

Тип `REAL` (план `PLAN_REAL.md` + `REAL_PROMPTS.md`, четыре этапа:
лексер/AST/парсер → слой типов в sema → codegen → корпус и документация)
реализован 2026-09-07 коммитами 0.1.11–0.1.14; оба временных файла удалены
коммитом 0.1.14, решения и долги перенесены сюда. Тип `BOOL` и логические
операции (план `PLAN_BOOL.md` + `BOOL_PROMPTS.md`, пять этапов: лексер/AST →
парсер → sema → codegen → корпус и документация) реализованы 2026-09-20 —
2026-09-21 коммитами 0.1.17–0.1.21; оба временных файла удалены коммитом
0.1.21, шесть решений и долги перенесены сюда.

Операторы `ELSIF` / `WHILE` / `REPEAT` / `EXIT` (план `PLAN_CTRL.md` +
`CTRL_PROMPTS.md`, четыре этапа: лексер/AST → парсер → sema и codegen →
эталоны и документация) реализованы 2026-10-06 коммитами 0.2.24–0.2.27; оба
временных файла удалены коммитом 0.2.27, семь решений и долги перенесены сюда.
Корпусный пример `examples/ctrl_all.st` был написан заранее, в коммите плана
(как в 0.0.32), и служил приёмкой этапа 3 — ожидаемые числа посчитаны руками
до первой строки кода.

`tools/tester/` — отдельный Qt/C++ проект (GUI-тестер), не часть транспилятора
и не документируется здесь: ведётся и дорабатывается пользователем
самостоятельно, в контекст и работу с этим файлом не включать.

## Команды

```bash
go build ./... && go vet ./...            # обязательно чисто
go test ./...                             # обязательно зелено перед коммитом
go run ./src examples/example.st          # генерация C в stdout
go run ./src -main -o out.c examples/example.st   # + драйвер main()
gcc -std=c99 -Wall -Wextra out.c && ./a.out       # самодостаточный файл
go run ./src -dump-ast examples/example.st        # печать AST вместо C
go test ./src/parser -update      # перегенерация эталонов *.ast (diff смотреть руками!)
go test ./src/codegen -update     # перегенерация эталонов *.c (diff смотреть руками!)
```

CLI-флаги `st2c`: `-o <file>` (по умолчанию stdout), `-main` (дописать
драйвер), `-scans N` (сколько раз драйвер зовёт `_step`, по умолчанию 1),
`-dump-ast` (печать дерева вместо генерации).

Позиционный аргумент `file.st` необязателен: без него исходник читается из
stdin — основной путь запуска (так его вызывает GUI-тестер: пишет ST в stdin
процесса, закрывает канал, ждёт C на stdout). Файл-аргумент — для ручного
запуска и отладки (`go run ./src examples/example.st` и т.п.).

### Ограничения языка
- Типы данных: скаляры `INT`, `REAL` и `BOOL`; любое другое имя типа обязано
  резолвиться в объявленный `FUNCTION_BLOCK` (переменная — экземпляр ФБ),
  иначе ошибка sema `unknown type`
- **Типизация строгая**: `INT` и `REAL` не смешиваются ни в присваивании, ни
  в арифметике, ни в сравнении, ни в аргументах — только явные конверсии
  `INT_TO_REAL(x)` / `REAL_TO_INT(x)` (встроенные функции, округление к
  ближайшему). Исключение — **адаптивный целый литерал**: в контексте REAL
  `0`, `1 / 2`, `r + 1` — вещественные (`1 / 2` = 0.5). `BOOL` с числами
  не смешивается вовсе: `b := 1`, `i := TRUE`, `b : BOOL := 0` — ошибки,
  адаптивного булева литерала и конверсий `BOOL` ↔ `INT` нет
- **Логические операции** `AND`, `OR`, `XOR`, унарный `NOT` и IEC-синоним
  `&` для `AND` — только над `BOOL` (`i AND j` над `INT` — ошибка, побитовых
  операций нет). Приоритет по IEC, от слабого к сильному: `OR` < `XOR` <
  `AND`/`&` < `= <>` < `< > <= >=` < `+ -` < `* /` < унарные (`-`, `NOT`) <
  постфиксы (`.`, вызов); `x > 1 AND y < 2` — `AND` над двумя сравнениями,
  `NOT a = b` — это `(NOT a) = b`
- Сравнение `BOOL`: `=` и `<>` разрешены (`IF done = enabled THEN`),
  порядковые `< > <= >=` над `BOOL` — ошибка `cannot order BOOL values`
- Условие `IF`, `ELSIF`, `WHILE` и `UNTIL` — любое выражение типа `BOOL`:
  сравнение, логическая связка, переменная, `NOT b`, член ФБ, вызов функции с
  возвратом `BOOL`; с `INT`/`REAL` — ошибка (`WHILE condition must be BOOL,
  got INT`). `FOR` только по `INT` (переменная, границы, шаг)
- POU: `PROGRAM` (struct состояния + `_init`/`_step`, живёт между сканами),
  `FUNCTION` (без состояния, возврат по IEC — присваивание имени функции),
  `FUNCTION_BLOCK` (тип с состоянием, экземпляры, вложенность)
- Конструкции: присваивание, `IF / ELSIF / ELSE`,
  `FOR ... TO ... [BY ...] DO`, `WHILE c DO ... END_WHILE`,
  `REPEAT ... UNTIL c END_REPEAT`, `EXIT;`; вызовы функций в выражениях
  `f(1, y := 2)`, вызов ФБ как оператор `inst(In := x, Out => y);`, доступ к
  члену экземпляра `inst.Out`
- `ELSIF` — сколько угодно ветвей, `ELSE` необязателен; срабатывает первая
  истинная. Старая форма `ELSE IF ... END_IF END_IF` работает по-прежнему и
  остаётся в AST **другим** деревом (`If` внутри `Else`, не `ElsIf`)
- `WHILE` проверяет условие перед каждой итерацией (ложно на входе — тело не
  выполняется ни разу); `REPEAT` выполняет тело хотя бы раз и проверяет
  `UNTIL` после тела. После `UNTIL c` точки с запятой **нет** (по грамматике
  IEC): `UNTIL c; END_REPEAT` — ошибка `expected END_REPEAT, got ;`. `;`
  после `END_WHILE`/`END_REPEAT` необязательна, как после `END_IF`/`END_FOR`
- `EXIT;` выходит из **ближайшего** объемлющего цикла (`FOR`, `WHILE` или
  `REPEAT`); `EXIT` внутри `IF`/`ELSIF` внутри цикла законен — `IF` циклом не
  считается. `EXIT` вне цикла — ошибка sema `EXIT outside of a loop`
- Арифметика `+ - * /`, сравнения `= <> < > <= >=`, логические
  `AND OR XOR NOT &`, унарный минус, скобки
- Литералы: десятичные целые и вещественные (`3.14`, `1.5E3`, `1e-3`; `1.`
  без дробной части — не вещественный), булевы `TRUE`/`FALSE`
  (регистронезависимы, как ключевые слова)
- Вложенность конструкций — любая (рекурсивный спуск даёт её «бесплатно»)

## Что реализовано (по пакетам)

**`src/main.go`** — CLI на пакете `flag`: `st2c [-o out.c] [-main]
[-scans N] [-dump-ast] file.st`. Конвейер: лексер → парсер
(`ParseSourceFile`) → sema (`Check`; все ошибки в stderr, выход с кодом 1) →
`codegen.Generate` → файл `-o` либо stdout. `-dump-ast` вместо генерации
печатает AST каждого POU через `String()` (прежнее поведение). Лексер
одноразовый (pull-модель), поэтому вывод потока токенов Этапа 1 остался в
git-истории, а не в `main`.

**`src/lexer/lexer.go`**
- `TokenType` (iota): `EOF`, `ILLEGAL`, `IDENT`, `INT_LIT`, `REAL_LIT`,
  операторы (`+ - * / > < = <= >= <>`, `:=`, `=>` (`ARROW`), `&` (`AMP` —
  синоним `AND`)), разделители (`: ; , ( )`, `.` (`DOT`)), 39 ключевых слов
  (включая `BY`, семейство `VAR_INPUT/VAR_OUTPUT/VAR_IN_OUT/VAR_TEMP`,
  квалификаторы `CONSTANT`/`RETAIN`, `FUNCTION`/`END_FUNCTION`,
  `FUNCTION_BLOCK`/`END_FUNCTION_BLOCK`, типы `INT`/`REAL`/`BOOL`, литералы
  `TRUE`/`FALSE`, логические `AND`/`OR`/`XOR`/`NOT`, управляющие `ELSIF`,
  `WHILE`/`END_WHILE`, `REPEAT`/`UNTIL`/`END_REPEAT`, `EXIT` — `DO` у `WHILE`
  тот же, что у `FOR`). Ключевое слово —
  идентификатор целиком: `AND1`, `NOTx`, `ORDER`, `BOOLEAN`, `WHILEX`,
  `EXITS`, `REPEATED`, `UNTIL1`, `END_WHILEX` остаются `IDENT`; `ELSE IF` —
  два токена, `ELSIF` — один
- `Token{Type, Literal, Line, Col}` — позиция 1-based, колонки в рунах
  (`lineStart` в лексере, сброс на `\n`)
- `NextToken()` — посимвольный разбор: пробелы/переносы, комментарии,
  двухсимвольные операторы через `peek()`, идентификаторы → ключевые слова
  (case-insensitive), числовые литералы. **Порядок веток `switch` значим**:
  ветка двухсимвольного оператора обязана стоять до односимвольного с тем же
  первым символом (`=>` до `=`, `<=`/`<>` до `<`) — Go проверяет `case` по
  порядку, при обратном порядке `=>` молча разберётся как `=` и `>`
  (зафиксировано тестом «arrow vs eq and gt»). `&` — односимвольная ветка,
  `&&` в ST нет, ловушки порядка у него нет
- Комментарии: блочные `(* ... *)` с вложенностью (3-я ред. IEC) и строчные
  `// ...`; незакрытый `(*` → `ILLEGAL`-токен с позицией начала; одиночные
  `(` и `/` остаются `LPAREN`/`SLASH`
- Числа — `readNumber` по грамматике IEC: `integer` → `INT_LIT`;
  `integer '.' integer [exp]` и `integer exp` → `REAL_LIT`
  (`exp = (e|E) [+|-] integer`). Дробная часть принимается, **только если
  за `.` идёт цифра**, экспонента — только если за `e`/`E` идёт `[+|-]`
  цифра; иначе откат к `INT_LIT`. Так `3.14` отличается от `inst.Out`,
  `1..10` (будущий `ARRAY`) лексится как `INT_LIT DOT DOT INT_LIT`,
  `1EXIT` не съедает хвост, `1.` — не REAL (по IEC), а `INT_LIT DOT`
- `tokenNames` для ключевых слов строится из `keywords` в `init()` — новое
  слово добавляется в одном месте; **не-ключевые токены (`REAL_LIT`, `AMP`
  и т.п.) вписываются в `tokenNames` руками**, иначе `String()` даст
  `UNKNOWN` в сообщениях парсера (у `AMP` это пиннит негативный тест
  парсера `x := & b` → `expected expression, got &`)

**`src/ast/ast.go`** — узлы дерева через интерфейсы:
- Интерфейсы `Node` (`String()`, `Line()`), `Statement`, `Expression`, `POU`;
  маркерные методы (`statementNode()` и т.п.) разделяют категории узлов на
  уровне типов
- Корень — `SourceFile{POUs []POU}`; `POU` реализуют `Program`, `Function`
  (`Name, ReturnType string, VarBlocks, Body, Tok`) и `FunctionBlock` (то же
  без `ReturnType`)
- `ast.Op` — собственный enum операций (`ADD … NE`, логические `AND`/`OR`/
  `XOR`, унарные `NEG`/`NOT`) с `String()`, возвращающим исходное написание:
  символ (`+`, `<=`, `<>`) либо слово (`AND`, `NOT`) — в golden `.ast`
  `Binary(AND)`, `Unary(NOT)`; AST отвязан от `lexer.TokenType`. Синоним `&`
  отображён в ту же `AND` и отдельного написания не имеет (решение 4 BOOL)
- Узлы: `Program` (`VarBlocks []*VarBlock`); `VarBlock{Kind VarKind,
  Constant, Retain bool, Decls}` — вид блока (`VAR`/`VAR_INPUT`/…) как данные;
  `VarDecl{Names []*Identifier, TypeName string, Init Expression}` — список
  имён (`a, b, c : INT;`) **узлами с собственными позициями** (иначе sema
  указывала бы на первое имя списка вместо дубликата), тип строкой,
  необязательный инициализатор (`x : INT := 5;`); `AssignStatement`
  (`Target Expression` — lvalue, пока всегда `*Identifier`, позже
  `IndexExpr`/`MemberExpr`); `IfStatement` (`Cond`, `Then`,
  `ElsIfs []*ElsIfClause`, `Else`); `ElsIfClause{Cond Expression, Then
  []Statement, Tok}` — **не** `Statement`: часть `IfStatement`, а не
  самостоятельный оператор (маркерного метода и `Line()` нет, как у `Arg`);
  `WhileStatement{Cond, Body, Tok}`; `RepeatStatement{Body, Cond, Tok}` —
  поля в порядке исходника (тело, потом условие); `ExitStatement{Tok}`;
  `ForStatement`
  (`Var *Identifier`, `Step Expression`, nil → шаг 1); `CallStatement`
  (`Call *CallExpr` — вызов ФБ как оператор); `Identifier`; `IntLiteral`
  (`Value int`); `RealLiteral{Value float64, Text string}` — `Text` хранит
  исходное написание, `String()` печатает `Real(<Text>)`, чтобы golden
  `.ast` не зависел от форматирования float в Go; `BoolLiteral{Value bool}` —
  `String()` печатает `Bool(TRUE)`/`Bool(FALSE)` всегда в верхнем регистре,
  независимо от написания в исходнике (golden не зависит от регистра);
  `BinaryExpr` (арифметика, сравнения и логические операции — единый тип,
  различаются `Op`); `UnaryExpr` (`NEG` — унарный минус, `NOT`; позже `+`);
  `MemberExpr{Base Expression,
  Member string}` (`inst.Out`); `CallExpr{Callee Expression, Args []*Arg}` и
  `Arg{Name string, Value Expression, Output bool}` — `Name == ""` для
  позиционного аргумента, `Output` для формы `name => lvalue`
- `String()` каждого узла рекурсивно печатает поддерево с отступами (формат
  golden-эталонов); поле `Tok lexer.Token` — якорь позиции. У `If` блок
  `ElsIf:` (`Cond:` + `Then:`) печатается **только при непустом списке** —
  иначе разъехались бы все прежние golden `.ast` с `IF` (решение 1 CTRL); у
  `While` метки `Cond:`/`Body:`, у `Repeat` — `Body:`/`Until:` (`Body:`, а не
  `Do:` как у `For`: ключевое слово `DO` у `WHILE` стоит после условия, и
  метка `Do:` после `Cond:` читалась бы как «тут был токен DO»; у `For`
  менять нельзя — поедут эталоны)

**`src/parser/parser.go`** — recursive descent:
- `New(*lexer.Lexer) *Parser`; `ParseSourceFile() (*ast.SourceFile, error)` —
  единственная точка входа: цикл по POU до EOF, диспетчер по стартовому
  ключевому слову (`PROGRAM`, `FUNCTION`, `FUNCTION_BLOCK`); мусор на верхнем
  уровне → ошибка
- Окно из двух токенов (`cur`/`peek`), хелперы `nextToken`/`expect`/`curIs`/`peekIs`
- Правила: `parseProgram`, `parseFunction` (`FUNCTION IDENT : type` +
  VAR-блоки + тело до `END_FUNCTION`; тип возврата через `parseType`),
  `parseFunctionBlock` (то же без типа возврата, до `END_FUNCTION_BLOCK`),
  `parseVarBlocks` (цикл по семейству `VAR*` через
  таблицу `varBlockKinds`, квалификаторы `CONSTANT`/`RETAIN`), `parseVarDecl`
  (список имён через запятую, тип, необязательный `:= init`), `parseType`
  (ключевые слова `INT`/`REAL`/`BOOL` или любой `IDENT` — пользовательские
  типы не падают, допустимость проверит sema), `parseStatements`,
  `parseStatement`, `parseIf`,
  `parseFor` (необязательный `BY step` перед `DO`), `parseWhile`
  (`WHILE expr DO {stmt} END_WHILE`), `parseRepeat`
  (`REPEAT {stmt} UNTIL expr END_REPEAT` — после условия **сразу**
  `expect(END_REPEAT)`, точка с запятой там не допускается), `parseExit`
  (`EXIT ;` — `;` обязательна, как у любого простого оператора)
- `parseIf` между `Then` и `ELSE` — цикл по `ELSIF`: каждая ветка пополняет
  `ElsIfs`. `ELSIF` после `ELSE` отвергается сам собой: тело `ELSE`
  заканчивается на `ELSIF` (он в `isBlockEnd`), а `expect(END_IF)` даёт
  `expected END_IF, got ELSIF`
- Оператор с идентификатора — `parseAssignOrCall`: сначала postfix-выражение
  через `parsePrimary`, затем по текущему токену: `CallExpr` + `;` →
  `CallStatement` (вызов ФБ как оператор); `:=` — присваивание, цель обязана
  быть `*Identifier` или `*MemberExpr` (`inst.In := 5;`)
- Выражения — Pratt / precedence climbing: одна `parseExpression(minPrec int)`
  + таблица `prec map[lexer.TokenType]int` (уровни по IEC, от слабого к
  сильному: `OR` 1 < `XOR` 2 < `AND`/`&` 3 < `= <>` 4 < `< > <= >=` 5 <
  `+ -` 6 < `* /` 7; логические уровни ниже всех остальных, относительный
  порядок прежних сохранён — golden `.ast` старых примеров не изменились);
  левая ассоциативность — правый операнд с `pr+1`; `binOps` переводит токен
  в `ast.Op`, причём `AND` и `AMP` дают одну `ast.AND`; `parseUnary` — по
  таблице `unaryOps` (`MINUS` → `NEG`, `NOT` → `NOT`), рекурсивно для обоих
  (`--x`, `NOT NOT b`, `NOT -x` разбираются, типы — за sema); унарный
  уровень сильнее любого бинарного (`NOT a = b` — `(NOT a) = b`) →
  `parsePrimary` (`IDENT`, `INT_LIT`, `REAL_LIT` через `strconv.ParseFloat`,
  `TRUE`/`FALSE` → `BoolLiteral`, `( expr )`). **Новый бинарный оператор =
  по строке в `prec` и `binOps`, унарный — строка в `unaryOps`**
- Постфиксы в `parsePrimary` (этап 3b): после атома цикл по `.` и `(` —
  `MemberExpr` (`inst.Out`) и `CallExpr`; связывают сильнее унарного минуса
  (`-f(x)` = `-(f(x))`). Аргументы — `parseCallArgs`/`parseCallArg`:
  различение по `peek` после `IDENT` — `name := expr` (вход),
  `name => lvalue` (выход; цель обязана быть `Identifier`/`MemberExpr`,
  иначе ошибка), иначе позиционное выражение; `f()` без аргументов допустим
- `isBlockEnd` включает `END_FUNCTION`/`END_FUNCTION_BLOCK`, `ELSIF`,
  `END_WHILE`, `UNTIL`, `END_REPEAT` — несовпадение закрывающего слова даёт
  внятную ошибку `expected END_FUNCTION_BLOCK, got …`. Список **плоский**:
  тело оператора кончается на любом терминаторе, а какой из них уместен —
  решает `expect` в правиле самой конструкции (`expected END_WHILE, got
  END_FOR`)
- Ошибки — **fail-fast**: поле `err`, `expect()`/`fail()` формируют сообщение
  с номером строки; `ParseSourceFile` возвращает первую ошибку
- `optionalSemicolon()` — необязательный `;` после
  `END_IF`/`END_FOR`/`END_WHILE`/`END_REPEAT`

**`src/sema/sema.go`** — семантический анализ между парсером и codegen:
- `Check(*ast.SourceFile) (*Info, []error)` — таблица имён
  **двухуровневая** (этап 4): первый проход строит глобальную таблицу POU
  (`map[string]ast.POU`, дубль имени POU любого вида — ошибка; имя
  встроенной функции `INT_TO_REAL`/`REAL_TO_INT` — ошибка `reserved name`),
  затем тела всех POU обходятся в порядке файла, каждое — со своей локальной
  таблицей; ошибки **копятся** (не fail-fast), все с позицией `line N:C`.
  `Info` — side-table для codegen: `Types map[ast.Expression]TypeKind` (тип
  каждого выражения; у адаптивного целого литерала — принятый тип контекста)
  и `UsedBuiltins map[string]bool` (какие конверсии реально вызваны — по
  этому codegen решает, эмитить ли хелпер в прологе). При ошибках `Info`
  неполна, codegen запускать нельзя
- Обе таблицы с ключом `strings.ToUpper(name)` — идентификаторы по IEC
  регистронезависимы (`Sum` = `sum`)
- **Тип — сущность** (слой типов, REAL этап 2): enum `TypeKind` — `Invalid`
  («тип не выведен, ошибка уже выдана» — гасит каскад выше по дереву),
  `Unknown` (контекст типа не задаёт), `Int`, `Real`, `Bool` (объявляемый
  тип с BOOL этапа 3; результат сравнения и логической операции), `FBInst`.
  `Symbol{Name, TypeName, Type TypeKind, Tok, FB}` — `TypeName` остаётся для
  текста сообщений. `builtinType(name)` — единственная точка «встроенные
  скаляры» (`INT`, `REAL`, `BOOL`); `isScalar(k)` — единственная точка
  перечисления типов-значений (обслуживает `scalarOnly` для подсказок
  `hintOf` и `returnKind` — функция может возвращать BOOL); новый скаляр —
  строка в `builtinType`, `isScalar` и в четырёх таблицах codegen
- **Вывод типов снизу вверх** — `typeOf(e, want TypeKind) TypeKind`
  (обёртка над `infer`, записывает результат в `Info.Types`). `want` — тип
  контекста: `IntLiteral` при `want == Real` становится `Real`
  (**адаптивный литерал**), иначе `Int` с проверкой диапазона (при
  `want == Invalid` диапазон не навязывается — нет каскада; контекст `Bool`
  литерал не меняет — адаптивного булева литерала нет, `b := 1` отвергнет
  присваивание); `RealLiteral` — `Real` с проверкой представимости в float32
  (округление к float32 не даёт бесконечности; сам максимум `3.4028235e38`
  законен); `BoolLiteral` — всегда `Bool`; `UnaryExpr NEG` над целым
  литералом — знак учитывается до проверки диапазона (`-32768`), тип
  литерала пишется в side-table отдельно; `UnaryExpr NOT` — операнд
  выводится с контекстом `Bool` и обязан быть `Bool` (`NOT requires a BOOL
  operand, got INT` на токене оператора), результат `Bool`; `BinaryExpr` —
  `inferBinary`, разведённая по классам операции: логическая (`isLogical`:
  `AND`/`OR`/`XOR` → `inferLogical` — оба операнда в контексте `Bool` без
  подсказки соседа, обязаны быть `Bool`, результат `Bool`; иначе
  `operator "AND" requires BOOL operands, got INT and INT` — `&` в сообщении
  зовётся `AND`), сравнение (`isComparison`: операнды одного типа, результат
  `Bool`; `Bool` допускается только для `=`/`<>`, порядковые (`isOrdering`)
  над `Bool` — `cannot order BOOL values (operands of "<" are BOOL and INT;
  BOOL is compared only with = and <>)` — типы в сообщении показывают, откуда
  в ловушке `a < b < c` взялся BOOL) и арифметика (операнды одного типа,
  возвращает его же; `Bool` — `is not applicable to BOOL`); `Bool` под
  минусом — ошибка; `MemberExpr` → тип члена, `CallExpr` → тип возврата
  функции / результат builtin. Совместимость с `want` проверяет
  **вызывающий**, знающий контекст (`checkAssign`, `checkArg`, условие,
  входы ФБ) — `typeOf` только выводит
- **Контекст операндов бинарной операции** — `hintOf(e)`: предварительный
  вывод без записи в side-table и без ошибок (тип переменной, члена,
  возврата функции, `Real` у вещественного литерала, `Bool` у булева
  литерала, сравнения, логической операции и `NOT`; `Unknown` для одних
  целых литералов). Подсказка соседа-операнда
  **приоритетнее** `want` сверху: `IF 1 > r` и `IF r > 1` симметричны, а
  `r := i + 1` даёт внятное «cannot assign INT to r», а не «INT и REAL в +»;
  `want` применяется только когда оба операнда без подсказки
  (`r := 1 / 2` — вещественное деление)
- Проверки типов: присваивание и инициализатор — тип значения равен типу
  цели (`checkAssign`; при смешении INT/REAL к сообщению добавляется
  подсказка `use INT_TO_REAL / REAL_TO_INT`; к ошибкам с BOOL подсказки нет
  — конверсий BOOL ↔ INT не существует); условия `IF`/`ELSIF`/`WHILE`/`UNTIL`
  обязаны быть `Bool` — любое выражение этого типа, не только сравнение.
  Единая проверка — хелпер **`checkCondition(kw, e)`**, ключевое слово попадает
  в сообщение (`IF condition must be BOOL, got INT`, `WHILE …`, `ELSIF …`,
  `UNTIL …`; позиция — начало выражения, `exprTok`); `FOR` —
  переменная, `Start`/`End`/`Step` только `Int`; аргументы функций
  (`checkArg`) и входы/выходы ФБ — тип равен типу входа/цели `=>` (BOOL
  проходит через `kindOf` → `builtinType` без отдельных правок: BOOL-входы,
  выходы, инициализаторы входов ФБ, BOOL-возврат функции). Позиция ошибки
  несовпадения операндов — токен оператора
- **Порядок обхода управляющих конструкций — порядок исходника** (ошибки sema
  копятся в нём): у `IfStatement` сначала условие и `Then`, затем каждая ветка
  `ELSIF` (условие, потом её тело), затем `Else`; у `WhileStatement` условие,
  потом тело; у `RepeatStatement` — **тело раньше** `UNTIL`
- **Счётчик циклов для `EXIT`** — поле `loops` в `checker`:
  `FOR`/`WHILE`/`REPEAT` делают `++` перед обходом тела и `--` после;
  `ExitStatement` при нуле → `EXIT outside of a loop` на токене `EXIT`. `IF` и
  `ELSIF` счётчик не трогают — `EXIT` внутри них законен. Между POU счётчик
  не протекает физически: `Check` создаёт **новый `checker` на каждый POU**
- Ветка `default:` в `checkStatement` — внутренняя ошибка
  `line N: sema: internal: unhandled statement %T` (без колонки: `c.errorf`
  принимает `lexer.Token`, а у `ast.Statement` есть только `Line()`).
  Симметрия с `unsupported statement` у `codegen.stmt`: новый тип оператора,
  забытый в sema, иначе дошёл бы до codegen непроверенным. Тестом не
  покрывается — маркерный метод `statementNode()` неэкспортирован, чужой пакет
  тип оператора подделать не может; страховка для будущих `CASE`/`RETURN`
- **Встроенные конверсии** — таблица `builtins` (имя → типы параметров и
  результат): `INT_TO_REAL(Int) Real`, `REAL_TO_INT(Real) Int`. Резолв
  callee в `checkCall`: `pous` → `builtins` → `syms`; только позиционные
  аргументы (именованный, `=>` — ошибка), число и типы по таблице; факт
  вызова — в `Info.UsedBuiltins`; в граф рекурсии builtins не попадают.
  Следствие адаптивного литерала: `REAL_TO_INT(3)` законно (3 → REAL)
- `Function`: имя функции регистрируется в её локальной таблице как
  **переменная возврата** с типом `ReturnType` (возврат по IEC — присваивание
  имени функции: `Add := x + y;`); `ReturnType` резолвится как тип
  объявления (неизвестное имя — `unknown type`, ФБ — отдельная ошибка
  «cannot return a function block»); параметр или переменная с именем
  функции — обычная ошибка дубликата. `FunctionBlock` обходится как тело со
  своей таблицей (объявленность, дубликаты, диапазоны, типы)
- Проверки имён: объявленность (ссылки в выражениях, цели присваиваний,
  переменная `FOR`), дубликаты объявлений (в т.ч. в разном регистре и между
  блоками; позиция ошибки — токен самого дублирующего имени, не первого в
  списке объявления), диапазон `INT` −32768..32767 для целых литералов,
  принявших тип `Int`
- **Резолв типов объявлений** (этап 6, `resolveType(name, tok)`):
  встроенные скаляры — через `builtinType`; любое другое имя ищется в
  глобальной таблице POU: `FunctionBlock` → переменная становится
  экземпляром ФБ (`Symbol.FB`), другой POU → ошибка `is not a type`, не
  найдено → `unknown type`. Инициализатор у экземпляра (`c : Counter := 5;`)
  — ошибка. `kindOf(name)` — молчаливый резолв для чужих объявлений (входы
  функций, члены ФБ, возврат callee): ошибку выдаёт проверка того POU, где
  тип объявлен
- Проверки вызова функции (`CallExpr`, этап 4). Резолв callee: **сначала
  глобальная таблица POU, потом локальная** (в обратном порядке переменная
  возврата молча проглотила бы прямую рекурсию `F := F(x);`); callee —
  локальная переменная → экземпляр ФБ, пропускается до этапа 6. Ошибки:
  необъявленная функция; вызов не-функции (имени PROGRAM/ФБ); `=>` к функции
  неприменим (выходов нет); позиционный аргумент после именованного;
  именованный аргумент с несуществующим входом; повторная привязка входа
  (дубль имени или именованный поверх позиционного); число аргументов ≠
  числу входов из `VAR_INPUT` — у функции **все входы обязательны** (у ФБ
  иначе: аргументы необязательны — этап 6). Значения аргументов выводятся
  с контекстом типа соответствующего входа (адаптивный литерал и диапазон
  работают) и обязаны совпасть с ним по типу
- **Запрет рекурсии** (по IEC функции нерекурсивны): при обходе тел функций
  собирается граф вызовов «функция → функция», затем DFS тремя цветами ловит
  прямую и взаимную рекурсию; ошибка на позиции замыкающего цикл вызова,
  одна на цикл
- **Члены экземпляров** (этап 6, `resolveMember`/`fbMember`): база `inst.X` —
  обязательно экземпляр ФБ (вложенный доступ `m.inner.sum` не
  поддерживается — ошибка); член ищется в `VAR_INPUT`/`VAR_OUTPUT` интерфейса
  (внутренние `VAR`/`VAR_TEMP` снаружи недоступны). Доступ направленный:
  вход — только запись, выход — только чтение; тип члена — тип контекста
  (`c.step := 40000` и `c.step := 2.5` ловятся)
- **Вызов ФБ как оператор** (этап 6, `checkFBCall`): callee — экземпляр ФБ из
  локальной таблицы (скаляр, имя POU, необъявленное имя — ошибка); аргументы
  **только именованные** (позиционный — ошибка): `name := expr` — только во
  вход (значение с типом входа как контекстом, тип обязан совпасть),
  `name => target` — только из выхода, цель проверяется как запись
  (`Identifier` или член-вход другого экземпляра) и обязана совпасть по
  типу с выходом; повторная привязка имени — ошибка. **Полнота списка не
  требуется**: `inst()` и `inst(step := 1)` законны — непереданный вход
  хранит значение с прошлого вызова, в этом смысл состояния ФБ
- **Экземпляр — не значение** (этап 6): чтение экземпляра в выражении,
  присваивание ему целиком и вызов в выражении (`x := c(...)` — у ФБ нет
  возвращаемого значения) — ошибки
- **Запрет циклической вложенности экземпляров** (этап 6,
  `checkInstanceCycles`): ФБ, прямо или косвенно содержащий экземпляр самого
  себя, дал бы в C struct бесконечного размера; DFS тремя цветами по графу
  «ФБ содержит ФБ», ошибка на объявлении, замыкающем цикл, одна на цикл

**`src/codegen/codegen.go`** — генерация C (весь язык):
- Контракт: `Options{Main bool, Scans int}`,
  `Generate(*ast.SourceFile, *sema.Info, Options) (string, error)`.
  Генератор предполагает чистый `sema.Check`: необъявленное имя здесь —
  внутренняя ошибка. `info == nil` допустим (генерация без sema — негативные
  тесты codegen со `skipSema`): литералы тогда целые, хелперы не эмитятся.
  Эмиттер `gen` — `strings.Builder`, уровень отступа, контекст текущего POU
  (таблица имён `vars` + признак `deref`), `info`, счётчик суффиксов
  временных `FOR`
- **Контекст эмиттера** (этап 5): у POU со состоянием (PROGRAM и ФБ)
  переменные — поля struct, обращение `self->x` (`deref == true`); у функции
  состояния нет, переменные локальные, обращение прямое `x`. Единая точка —
  `g.ref(vi)`; ею пользуются выражения, `_init` и `FOR`
- **PROGRAM и ФБ — общий `stateInfo`** (этап 7): typedef struct + `_init` +
  функция шага; различается только имя шага (`stepName`: `_step` у PROGRAM,
  `_body` у ФБ). Оболочки `stateInfo` всех ФБ строятся до заполнения таблиц
  переменных (`collectVars`): экземпляр может быть объявлен выше своего ФБ по
  файлу, а тип объявления, найденный среди ФБ, делает `varInfo` экземпляром
  (`varInfo.fb`) — полем-struct, а не скаляром
- **Два прохода** (решение 5): сначала все `typedef struct` + прототипы
  (`Name_init`/`Name_step`/`Name_body`, сигнатура у FUNCTION), затем все
  тела — порядок POU и взаимные ссылки не важны. Исключение внутри первого
  прохода (этап 7): struct владельца содержит struct экземпляра **по
  значению**, поэтому typedef вложенного ФБ обязан идти раньше — объявления
  эмитятся post-order DFS по вложенности (топологическая сортировка;
  прототипы это не решают, отсутствие циклов гарантирует sema)
- **`FUNCTION_BLOCK` → struct + `Name_init`/`Name_body`** (этап 7): все
  VAR-блоки (входы, выходы, внутренние) — поля одной структуры; экземпляр
  `inst : Counter;` во владельце — поле `Counter inst;`, `_init` владельца
  рекурсивно зовёт `Counter_init(&self->inst)` (решение 3; инициализатор у
  экземпляра отвергла sema). `MemberExpr` в выражении → `self->inst.count`
  (и чтение выхода, и цель присваивания `inst.In := …` — обе формы идут
  через `expr`). Драйвер `-main` пропускает поля-экземпляры (решение 4)
- **`CallStatement` — вызов ФБ** (этап 7) разворачивается в три части:
  присваивания входов `self->inst.step = <expr>;` (в порядке аргументов),
  вызов тела `Counter_body(&self->inst);`, выгрузка выходов
  `self->y = self->inst.count;` (в порядке аргументов). Адрес — `&g.ref(vi)`,
  поэтому вызов внутри ФБ даёт `&self->inner`. Корректность привязок (имена,
  направление, только именованные) гарантирует sema — дыры здесь внутренние
  ошибки
- **`FUNCTION` → обычная C-функция** (этап 5): `funcInfo` — параметры из
  `VAR_INPUT` в порядке объявления (порядок задаёт и сигнатуру, и раскладку
  именованных аргументов), локальные из `VAR`/`VAR_TEMP`, возвратная
  переменная одноимённа функции (возврат по IEC — присваивание её имени) —
  в C локальная, легально затеняющая саму функцию (рекурсию отсекла sema):
  объявляется первой строкой `= 0`, `return` — последней. Локальные
  объявляются `= 0`, затем инициализаторы — присваиваниями в порядке
  объявления (та же семантика, что у `_init`); инициализаторы `VAR_INPUT`
  игнорируются (все входы по sema обязательны). `VAR_OUTPUT`/`VAR_IN_OUT` в
  FUNCTION — ошибка codegen с позицией. Функция без параметров → `(void)`
- **Вызов `CallExpr`** (этап 5) → `Name(a, b)`: именованные аргументы
  раскладываются в позиционные по порядку `VAR_INPUT` (полноту, уникальность
  и «позиционные раньше именованных» гарантирует sema — дыры в раскладке
  здесь внутренние ошибки); вызов — первичное выражение, своих скобок не
  получает
- **Таблицы типов — единственные точки маппинга**: `cTypes` (`cType()`:
  `INT` → `int16_t`, `REAL` → `float`, `BOOL` → `_Bool` — ключевое слово
  C99, `#include` не требует), `cWideTypes` (`cWideType()`: счётчик `FOR` —
  `INT` → `int32_t`; `REAL` и `BOOL` здесь нет сознательно — `FOR` по ним
  отвергает sema, ошибка `cWideType` остаётся внутренней защитой), `cZeros`
  (`zeroLiteral()`: `0` / `0.0f` / `0` — явная инициализация полей и
  локальных), `cFormats` (`cFormat()`: `%d` / `%g` / `%d` — печать в
  драйвере; `_Bool` в varargs промоутится до `int`, BOOL печатается `0`/`1`).
  Литералов `int16_t`/`float`/`_Bool`/`0` нет больше нигде — новый тип =
  строка в четырёх таблицах. Неизвестный тип (`MyType`) — ошибка с позицией
  (внутренняя защита: с этапа 6 его первым ловит sema)
- **Литералы**: `RealLiteral` → `cFloatLit(v)` — `FormatFloat(v, 'g', -1,
  32)` (кратчайшее написание, восстанавливающее float32) + суффикс `f`; если
  в результате нет ни `.`, ни `e`/`E` (`2.0` → `"2"`), перед `f`
  дописывается `.0` — иначе `2f` в C невалидно (большие целые дают
  экспоненту `1e+06f`, `.0` не нужен). `IntLiteral` при
  `info.Types[e] == sema.Real` (адаптивный литерал) — тоже через
  `cFloatLit`: `r := 1 / 2` → `(1.0f / 2.0f)`; иначе `strconv.Itoa`.
  `BoolLiteral` → `1` / `0` (`_Bool` — арифметический тип, `<stdbool.h>` не
  нужен)
- **Встроенные конверсии** — `builtinCall` (callee не найден среди функций
  файла): `INT_TO_REAL(x)` → `((float)(x))` (тип берётся из `cType("REAL")`),
  `REAL_TO_INT(x)` → `st_real_to_int(x)` — static-хелпер округления к
  ближайшему (от нуля) `(int16_t)(v >= 0.0f ? v + 0.5f : v - 0.5f)`, без
  `<math.h>`/`-lm` (`lroundf` не слинкуется в `TestGCC`). `emitHelpers`
  эмитит его после `#include` **только при `Info.UsedBuiltins["REAL_TO_INT"]`**
  — иначе `-Wall` даст `-Wunused-function`. Имя хелпера внесено в
  `reservedCNames`: `mapName` пропускает `st_`-имена как есть, и
  пользовательский `st_real_to_int` уходит в `st_st_real_to_int`
- **Маппер имён `mapName`** (решение 8) — через него проходит каждое имя
  (POU, переменные/поля): таблица из 32 ключевых слов C99 + имена
  `<stdint.h>` + `main` + `self` + `st_real_to_int`; совпадение с таблицей ИЛИ префикс `__`
  (в C зарезервирован за реализацией) → префикс `st_`; склейка имён после
  префиксации (`switch` при объявленном `st_switch`) — ошибка; не-ASCII
  имя — ошибка с позицией. Ссылки эмитятся каноническим написанием из
  объявления (ключ `ToUpper`) — регистронезависимость IEC не может дать
  разные C-идентификаторы
- `Name_init` (решение 3): каждая переменная в порядке объявления —
  инициализатор либо явный ноль своего типа (`zeroLiteral`: `0` / `0.0f`;
  C-выход не зависит от памяти вызывающего); инициализатор
  объявления-списка (`a, b, c : INT := 7`) применяется к каждому имени
- Выражения: `Identifier` → `self->x`; скобки вокруг каждой бинарной и
  унарной операции; таблица `cOps`: `EQ`→`==`, `NE`→`!=`, `AND`→`&&`,
  `OR`→`||`, `XOR`→`!=` (не `^`: на `_Bool` то же самое, но не зависит от
  нормализации значения, если BOOL переедет на `uint8_t`), остальные
  совпадают; таблица `cUnaryOps`: `NEG`→`-`, `NOT`→`!`. Скобки вокруг
  каждой операции означают, что `a && b || c` без скобок не возникает и
  `-Wparentheses` молчит; короткое замыкание `&&`/`||` ненаблюдаемо
  (функции ST без состояния и побочных эффектов, ФБ в выражениях не
  вызываются). `reservedCNames` править не пришлось: `_Bool` там уже был, а
  `TRUE`/`FALSE`/`AND`/`OR`/`XOR`/`NOT` — ключевые слова ST и переменными
  быть не могут
- `IF` → `if (…) {…} else {…}` (без `else` при `Else == nil`); ветки `ElsIfs`
  — **плоская** цепочка `} else if (<cond>) {` между `Then` и `else`, а не
  матрёшка `else { if … }` (следствие решения 1 CTRL: `ELSIF` хранится
  списком). `WHILE` → `while (<cond>) {…}` — условие вычисляется перед каждой
  итерацией, в отличие от границ `FOR`; `REPEAT` → `do {…} while (!<cond>);`,
  причём отрицание пишется всегда как `!(%s)`: у бинарной операции `g.expr`
  уже даёт свои скобки (`!((a > b))`), у переменной — нет (`!(self->b)`),
  двойные скобки `-Wparentheses` не смущают. `EXIT` → `break;` плюс
  внутренняя защита «sema must reject this» по счётчику `loops` в `gen`
  (при нуле — `codegen: internal: EXIT outside of a loop`; без неё обход sema
  через `skipSema` дал бы C, который gcc отвергнет невнятным `break statement
  not within loop or switch`). `loops` сбрасывается там же, где `forSeq` — в
  `emitInit`/`emitStep`/`emitFunction`: `gen` один на весь файл, «нового
  объекта на каждый POU», как в sema, здесь нет; `++` нужен и в `forStmt`
  вокруг тела, иначе `EXIT` в `FOR` упёрся бы в эту самую защиту; `FOR` — по
  решению 6: блок с временными `__iN`/`__endN`/`__stepN` типа `cWideType`
  (границы и шаг вычисляются один раз до входа; широкий счётчик не
  переполняется у границы `INT` — наивный `int16_t` даёт бесконечный цикл
  на 32767), направление тернарником `__stepN >= 0 ? <= : >=`, копия
  счётчика в переменную цикла первой строкой тела. При тривиально-константном
  шаге (`constStepSign`: шаг опущен → 1, литерал, унарный минус литерала)
  тернарник свёрнут в `<=` / `>=`; шаг-выражение оставляет тернарник
- Драйвер `-main` (решение 4): первая `PROGRAM` файла (нет PROGRAM —
  ошибка); `main()` зовёт `_init`, затем `-scans` раз `_step`, после каждого
  скана печатает все скалярные поля PROGRAM в порядке объявления строками
  `имя=значение` (оригинальное ST-имя, не переименованное C-поле);
  спецификатор — по типу поля из `cFormats`: `%d` для `INT`, `%g` для
  `REAL` (6 значащих цифр: `2.5`, `0.6875`, `1500`, `0`), `%d` для `BOOL`
  (`1`/`0`). Локальная переменная драйвера `scan` не конфликтует с
  одноимённым полем PROGRAM: поля читаются через `st.scan`, у членов struct
  своё пространство имён

void Example_step(Example *self) {
    ...

        int32_t __i0 = 1, __end0 = 5, __step0 = 1;

}

## Архитектурные решения (зафиксированы — не переоткрывать)

- **AST остаётся синтаксическим.** Результаты семантики (выведенные типы) —
  side-table `sema.Info{Types map[ast.Expression]TypeKind, UsedBuiltins}`,
  не поля узлов; `Check` возвращает её, `Generate` принимает.
- **Регистронезависимость** IEC: ключевые слова нормализует лексер,
  переменные — sema (ключ таблицы `ToUpper`); оригинальное написание
  сохраняется для сообщений об ошибках.
- **Парсер fail-fast, sema копит ошибки.** Восстановление после ошибок
  парсера отложено: поле `err` расширяется до `errs []error` без переделки
  архитектуры (synchronize до ближайшего `;`/`END_*`).
- **Контракты sema и codegen**: `sema.Check(*ast.SourceFile) (*Info,
  []error)`; `type Options struct { Main bool; Scans int }`,
  `codegen.Generate(*ast.SourceFile, *sema.Info, Options) (string, error)`
  (форма с `Info` — с 0.1.12/0.1.13; `nil` info допустим для генерации без
  sema); рекурсивный обход по образцу `String()`. Codegen работает в
  **два прохода** (решение 5): все `typedef` + прототипы, затем все тела —
  ST не требует объявления раньше использования, C требует.
- **Маппинг на C**: `INT` → `int16_t` (`#include <stdint.h>`), `REAL` →
  `float` (32 бита по IEC; `LREAL` → `double` оставлен на будущее),
  вещественные литералы с суффиксом `f` (без double-арифметики с
  последующим усечением), `BOOL` → `_Bool` (`TRUE`/`FALSE` → `1`/`0`);
  `=` → `==`, `<>` → `!=`, `AND` → `&&`, `OR` → `||`, `XOR` → `!=`,
  `NOT` → `!`; скобки вокруг каждого `BinaryExpr`/`UnaryExpr` (надёжность
  важнее читаемости C-выхода); `FUNCTION` → обычная C-функция (возврат через
  одноимённую локальную переменную, именованные аргументы вызова
  раскладываются в позиционные по порядку `VAR_INPUT`);
  `PROGRAM` → `typedef struct` состояния + `Name_init(Name *self)` +
  `Name_step(Name *self)` (решение 2: переменные POU живут между сканами
  PLC); `FUNCTION_BLOCK` → ровно та же форма с шагом `Name_body(Name *self)`
  (все VAR-блоки — поля struct; один механизм на PROGRAM и ФБ). Экземпляр —
  поле-struct владельца **по значению**, поэтому typedef эмитятся в
  топологическом порядке вложенности; вызов ФБ-оператора разворачивается в
  «входы → тело → выходы». Маппинг типов — только через таблицы
  `cTypes`/`cWideTypes`/`cZeros`/`cFormats`, литералов C-типов и нулей в
  коде нет.
- **Инициализаторы → отдельная `Name_init`** (решение 3), не C-инициализатор
  структуры: работает для неконстантных инициализаторов, вложенный экземпляр
  ФБ рекурсивно зовёт свой `_init`; переменные без инициализатора
  обнуляются явно.
- **Драйвер `-main`/`-scans`** (решение 4): без флага — библиотечный `.c`;
  с `-main` файл самодостаточен для `gcc`. Драйвер получает первая PROGRAM
  файла; печатает **только скалярные поля самой PROGRAM, в порядке
  объявления, после каждого скана**, по строке `имя=значение` — правило
  зафиксировано, чтобы `.expected` не поехали, когда struct станет вложенным
  (вложенные экземпляры ФБ не разворачиваются). Формат значения — часть
  контракта `.expected`: `%d` для `INT`, `%g` для `REAL` (6 значащих цифр,
  детерминированно; в примерах брать величины, точные в двоичном
  представлении).
- **`FOR` — счётчик шире переменной цикла** (решение 6): границы и шаг — во
  временных `__iN`/`__endN`/`__stepN` типа `cWideType` (вычисляются один раз
  до входа, как требует IEC); наивный `int16_t`-счётчик у границы диапазона
  переполняется и цикл не завершается (проверено, gcc 15.2); направление —
  тернарником по знаку шага, при тривиально-константном шаге свёрнуто в
  `<=` / `>=`. Побочное следствие: изменение переменной цикла в теле не
  влияет на число итераций.
- **Маппер имён ST → C** (решение 8): каждое имя проходит через `mapName`;
  ключевые слова C99 + `<stdint.h>` + `main` + `self` и любой идентификатор
  с префиксом `__` получают префикс `st_`; склейка после переименования —
  ошибка, не-ASCII — ошибка. Без этого коллизия всплыла бы через несколько
  этапов как «случайная» ошибка `gcc`.
- **Корпус примеров един** (решение 9): `.st` только в `examples/`, в
  `testdata/` пакетов — только эталоны.
- **Правила ФБ в sema** (этап 6): тип объявления, отличный от встроенного
  скаляра (`INT`/`REAL`/`BOOL`), обязан
  резолвиться в объявленный `FUNCTION_BLOCK` — переменная становится
  экземпляром. Вызов ФБ — только оператором и **только с именованными
  аргументами** (позиционные не поддерживаются — решение); список аргументов
  **необязателен и может быть неполным**: непереданный вход сохраняет
  значение с прошлого вызова (у функций наоборот — все входы обязательны).
  Доступ к экземпляру извне направленный: вход — только запись, выход —
  только чтение; внутренние `VAR` недоступны; экземпляр целиком — не
  значение и не lvalue. Циклическая вложенность экземпляров запрещена
  (struct в C был бы бесконечного размера) — codegen полагается на её
  отсутствие при топологической сортировке typedef.
- **Слой типов — строгий** (REAL, решение 1): тип — enum `TypeKind` в
  sema, вывод снизу вверх (`typeOf`/`hintOf`), side-table `Info`; неявных
  преобразований между `INT` и `REAL` нет ни в одном контексте — только
  встроенные `INT_TO_REAL`/`REAL_TO_INT`. Без вывода типов второй скаляр
  ломал бы модель: `i := r` молча усекалось бы, `r := 1/2` давало бы 0.
  Новый скаляр = строка в `builtinType` и `isScalar` sema и в четырёх
  таблицах codegen поверх этого слоя (так добавлен `BOOL`).
- **Адаптивный целый литерал** (REAL, решение 2): литерал принимает тип
  контекста — `r := 0`, `r := 1 / 2` (0.5, codegen эмитит `(1.0f / 2.0f)`),
  `g(v := 1)`, `REAL_TO_INT(3)` законны; принятый тип хранится в
  side-table. Подсказка соседа-операнда приоритетнее контекста сверху
  (`r := i + 1` — ошибка на присваивании, а не «INT и REAL в +»).
- **`REAL` = `float`** (REAL, решение 3): 32 бита по IEC, литералы с
  суффиксом `f`; `LREAL` = `double` — отдельный тип на будущее.
- **Конверсии с округлением по IEC** (REAL, решение 4): `INT_TO_REAL` →
  `(float)`, `REAL_TO_INT` → static-хелпер `st_real_to_int` (к ближайшему,
  половина — от нуля), эмитится только при фактическом вызове; без
  `<math.h>` и `-lm` (`TestGCC` линкует без `-lm`).
- **`FOR` остаётся целочисленным** (REAL, решение 5): у REAL нет широкого
  счётчика решения 6, а накопление ошибки шага делает число итераций
  непредсказуемым; `cWideTypes` для REAL сознательно пуст.
- **Условие `IF` обязано быть BOOL** (REAL, решение 6) — изначально только
  результатом сравнения; с работой по BOOL — любым выражением типа BOOL
  (переменная, `NOT`, логическая связка, член ФБ, вызов).
- **Набор логических операций** (BOOL, решение 1): `AND`, `OR`, `XOR`,
  `NOT` и IEC-синоним `&` для `AND`. Приоритет по IEC, от слабого к
  сильному: `OR` < `XOR` < `AND`/`&` < `= <>` < `< > <= >=` < `+ -` <
  `* /` < унарные (`-`, `NOT`) < постфиксы (`.`, вызов). Логические уровни
  легли ниже всех прежних — относительный порядок старых уровней сохранён,
  golden `.ast` не изменились.
- **`BOOL` → `_Bool`** (BOOL, решение 2): ключевое слово C99, новых
  `#include` не требует — golden `.c` всех прежних примеров остались
  побайтово прежними (регрессионный сигнал этапа 4). `_Bool`
  самонормализуется (любое ненулевое хранится как ровно 1), поэтому `%d` в
  драйвере печатает `0`/`1`; ноль — `0` в `cZeros`. `bool` + `<stdbool.h>`
  отвергнут: либо лишний include во всех эталонах, либо условная эмиссия
  include ради читаемости.
- **Логические операции в C** (BOOL, решение 3): `AND` → `&&`, `OR` → `||`,
  `NOT` → `!`, `XOR` → `!=`. `!=` вместо `^` сознательно: на `_Bool` то же
  самое, но не зависит от нормализации значения, если BOOL когда-нибудь
  переедет на `uint8_t`. Короткое замыкание `&&`/`||` ненаблюдаемо: функции
  ST без состояния и побочных эффектов, ФБ в выражениях не вызываются
  (проверяет sema) — невычисление правого операнда ничем себя не проявляет.
- **`&` не оставляет следа в AST** (BOOL, решение 4): токены `AND` и `AMP`
  отображаются в одну `ast.AND`; в сообщениях sema `&` зовётся `AND`.
  Обратная печать исходника — задача будущего форматтера (у него уже есть
  такой же долг: литерал ключевых слов приводится к верхнему регистру).
- **Адаптивного булева литерала нет** (BOOL, решение 5): адаптивность
  целого литерала (REAL, решение 2) касается только пары INT/REAL.
  `b : BOOL := 1;`, `i := TRUE;`, `IF i THEN` с INT — ошибки sema; к ним
  не добавляется подсказка про конверсии. Конверсий `BOOL_TO_INT` /
  `INT_TO_BOOL` нет (долг; таблица `builtins` к ним готова).
- **Сравнение BOOL** (BOOL, решение 6): `=` и `<>` над BOOL **разрешены**
  (по IEC равенство булевых законно и нужно на практике:
  `IF done = enabled THEN`), порядковые `< > <= >=` над BOOL — **ошибка**
  `cannot order BOOL values`. Запрет порядковых сохраняет диагностику
  ловушки `a < b < c`: она разбирается как `(a < b) < c`, левый операнд —
  BOOL, ошибка остаётся, а типы операндов в сообщении показывают, откуда он
  взялся. В codegen решение не стоит ничего: `==`/`!=` в `cOps` уже были.
- **`ELSIF` — явный список в AST** (CTRL, решение 1): у `IfStatement` поле
  `ElsIfs []*ElsIfClause`, а не вложенные `IF` внутри `Else`. Причина —
  «AST остаётся синтаксическим»: склейка во вложенный `IF` лишила бы дерево
  различия между `ELSIF` и `ELSE IF … END_IF` (разный текст программы,
  будущий форматтер не вернёт написание). Вторая выгода — в C плоская цепочка
  `else if`, а не матрёшка `else { if … }`. `String()` печатает `ElsIf:`
  **только при непустом списке** — поэтому golden `.ast` всех прежних
  примеров не изменились.
- **Условия `ELSIF`/`WHILE`/`UNTIL` — по правилу условия `IF`** (CTRL,
  решение 2): любое BOOL-выражение, `INT`/`REAL` — ошибка. Одна функция
  `checkCondition(kw, e)` в sema, ключевое слово попадает в сообщение
  (`WHILE condition must be BOOL, got INT`); сообщение для `IF` осталось
  побайтово прежним — прежние тесты не правились.
- **`WHILE` → `while`** (CTRL, решение 3): условие вычисляется **перед каждой
  итерацией** заново — в отличие от границ `FOR`, которые по решению 6
  считаются один раз до входа. Ложно на входе — тело не выполняется ни разу.
- **`REPEAT … UNTIL c` → `do { … } while (!(c));`** (CTRL, решение 4): тело
  хотя бы раз, условие после тела; смысл `UNTIL` — «повторять, **пока не**»,
  поэтому в C условие продолжения отрицается. Отрицание пишется всегда как
  `!(…)`, двойные скобки у сравнения не мешают. После `UNTIL c` точки с
  запятой по грамматике IEC нет: `UNTIL c; END_REPEAT` — ошибка.
- **`EXIT` → `break`** (CTRL, решение 5): выход из **ближайшего** объемлющего
  цикла; `EXIT` вне цикла — ошибка sema `EXIT outside of a loop` (счётчик
  `loops`), плюс внутренняя защита в codegen. `EXIT` внутри `IF`/`ELSIF`
  внутри цикла законен — у `if` в C своего `break` нет. С `FOR` работает
  потому, что обёртка `{ … }` вокруг `for` (решение 6) — **блок, а не цикл**.
- **`;` после `END_WHILE`/`END_REPEAT` необязательна** (CTRL, решение 6) — как
  после `END_IF`/`END_FOR` (`optionalSemicolon`).
- **`goto` в сгенерированном C не бывает никогда** (CTRL, решение 7).
  Сейчас единственные конструкции C, перехватывающие `break`, — циклы,
  полученные из циклов ST, поэтому `EXIT` — это всегда просто `break`. Когда
  появится `CASE` через C-`switch`, тот тоже начнёт перехватывать `break`, и
  `EXIT` внутри него (относящийся к циклу **снаружи** `CASE`) передаётся
  **флагом выхода** `__exitN`: `EXIT` поднимает флаг и выходит из `switch`,
  сразу после `switch` — `if (__exitN) break;`, уже из цикла. Проверено на
  gcc: наивный второй `break` молча выходит из `switch` вместо цикла
  (бесконечный цикл, без предупреждений), версия с флагом ведёт себя как ST.
  Флаг нужен **только** при `EXIT` внутри `CASE` — это видно из дерева, так
  что обычные `CASE` останутся чистыми. `goto` решил бы это одной строкой, но
  прыжок в произвольное место функции отвергнут осознанно.

  `builtinType` и `isScalar` sema и в четырёх таблицах codegen
  (`cTypes`/`cWideTypes`/`cZeros`/`cFormats`) поверх слоя типов; `TypeSpec`
  в AST (`ARRAY [1..10] OF INT` и т.п.; лексер уже разбирает `1..10` как
  `INT_LIT DOT DOT INT_LIT`).
- **Операторы дальше**: `CASE / RETURN` — встают в `parseStatement` и
  `isBlockEnd` независимо друг от друга. У `CASE` два отдельных вопроса, оба
  решаются в его плане: (1) `EXIT` внутри `CASE` — C-`switch` перехватывает
  `break`, поэтому `EXIT`, относящийся к циклу снаружи, идёт через **флаг
  выхода `__exitN`** (решение 7), `goto` не рассматривается; (2) **диапазоны
  меток** `1..5:` — у `switch` в C99 их нет: расширение GCC `case 1 ... 5:`
  непереносимо, развёртка в список `case` по стандарту, но `1..30000` даст
  30000 меток, возможен гибрид (списки меток `1, 3, 5:` проблемы не
  составляют). Лексер уже разбирает `1..5` как `INT_LIT DOT DOT INT_LIT`.
  Дальше:
  `MOD` и `**` — строка в `prec`/`binOps` парсера и в `cOps` codegen (`**`
  без C-оператора — потребует хелпера); конверсии `BOOL_TO_INT` /
  `INT_TO_BOOL` — строки в таблице `builtins` sema и в `builtinCall`
  codegen; восстановление после ошибок парсера.

## Известные долги (сознательно отложены)

- Литерал ключевых слов приводится к верхнему регистру — оригинал теряется
  (важно для будущего форматтера/сорсмапов). Той же природы: `&` неотличим
  от `AND` в AST (решение 4 BOOL) — форматтер не восстановит написание.
- Нет конверсий `BOOL_TO_INT` / `INT_TO_BOOL`: BOOL с числами не
  смешивается ни в одном контексте, а перевести флаг в число (или
  ненулевое — в флаг) нечем, кроме `IF`. Таблица `builtins` sema и
  `builtinCall` codegen к ним готовы.
- `AND`/`OR`/`XOR`/`NOT` — только булевы: побитовых операций над `INT` нет
  (`i AND 255` — ошибка sema `requires BOOL operands`); добавлять вместе с
  битовыми типами (`BYTE`/`WORD`) и их литералами (`16#FF`).
- Нет `MOD` и `**` — арифметика только `+ - * /`.
- **Бесконечный цикл внутри скана не диагностируется**: `WHILE TRUE` без
  `EXIT` или условие, которое никогда не станет ложным, вешают программу
  целиком — сторожевого таймера (watchdog) нет, и у скана нет предела времени.
  В тестах это ловит только `runTimeout` у `TestGCC` (10 с), поэтому ручной
  запуск сгенерированного бинаря идёт под `timeout 10`.
- **Недостижимый код после `EXIT`** (`EXIT; x := 1;` → `break; x = 1;`) не
  диагностируется ни sema, ни gcc: `-Wunreachable-code` не входит в
  `-Wall`/`-Wextra` и в современном gcc не работает — проверено.
- `UNTIL c;` с точкой с запятой перед `END_REPEAT` (диалект CODESYS) не
  принимается — по грамматике IEC её там нет (решение 4 CTRL).
- Драйвер `-main` печатает BOOL как `1`/`0` (`%d` по `cFormats`), а не
  `TRUE`/`FALSE` — формат зафиксирован в `.expected` (`bool_all`, `ctrl_all`),
  менять только вместе с эталонами.
- Числовые литералы — только десятичные (целые и вещественные). Нет
  `16#FF`, `2#1010`, `1_000`, `INT#5`, `T#1s`, строк с `$`-экранированием —
  добавлять вместе с типами, которым они нужны (диспетчеризация в
  `readNumber`).
- `IntLiteral.Value` — `int`; для литералов вне `int64` и типизированных
  литералов понадобится хранить исходную строку (у `RealLiteral` `Text`
  уже есть).
- Нет `LREAL` (`double`): `REAL` — единственный вещественный тип; слой
  типов и таблицы codegen к добавлению готовы.
- Деление REAL на `0.0` даёт `inf`/`nan` по правилам C без диагностики (как
  и целочисленное деление на ноль — UB, см. ниже).
- Сравнение REAL через `=`/`<>` не предупреждается: `-Wfloat-equal` не
  входит в `-Wall`/`-Wextra`, sema тоже молчит; в корпусе такие сравнения
  только с величинами, точными в двоичном представлении.
- Экземпляр ФБ в `VAR` функции sema пропускает (тип резолвится как обычно),
  хотя функция по IEC без состояния; падает уже в codegen
  (`no C mapping for type` — `funcInfo` сознательно не резолвит типы-ФБ).
  Честный запрет — вместе с семантикой видов блоков по типам POU.
- Член интерфейса ФБ сам может быть экземпляром ФБ (`sub : Inner;` в
  `VAR_INPUT`) — sema не запрещает; codegen эмитит такое поле как вложенный
  struct (топологический порядок и рекурсивный `_init` его учитывают), но
  передать в него значение извне нельзя (экземпляр — не значение), т.е.
  конструкция инертна. Честный запрет — вместе с семантикой видов блоков.
- `VAR_IN_OUT`-члены ФБ снаружи недоступны (`fbMember` смотрит только
  `VAR_INPUT`/`VAR_OUTPUT`) — согласуется с тем, что семантики «по ссылке»
  у `VAR_IN_OUT` нет вовсе; в MVP не использовать.
- Локальная переменная (или параметр) функции с именем другого POU затеняет
  его в C: sema не сверяет локальную таблицу с таблицей POU, а в C локальное
  объявление законно перекрывает функцию — вызов затенённой функции ниже по
  телу упадёт в `gcc` («called object is not a function»).
- Инициализаторы `VAR_INPUT` у функций codegen игнорирует: значение параметра
  приходит от вызывающего, все входы по sema обязательны; дефолты входов —
  вместе с правом sema их пропускать.
- `a < b < c` разбирается парсером левоассоциативно (зафиксировано тестом);
  sema отвергает это как `cannot order BOOL values (operands of "<" are BOOL
  and INT; BOOL is compared only with = and <>)` — типы операндов
  показывают, откуда взялся BOOL, но запись `a < b AND b < c` сообщение не
  подсказывает.
- Свёртка констант отсутствует: `--32768` пройдёт проверку диапазона;
  направление `FOR` сворачивается только при тривиально-константном шаге
  (`constStepSign`), шаг-выражение вроде `BY -(1)` оставляет тернарник.
- Лексер принимает не-ASCII идентификаторы (`unicode.IsLetter`):
  `переменная : INT;` молча проходит фронтенд; codegen отвергает такие имена
  ошибкой с позицией (решение 8) — транслитерация отложена.
- **Деление на ноль** (`INT`) — поведение C (UB), проверки времени
  выполнения нет.
- **Переполнение `INT`** — `int16_t` промоутится до `int`, результат
  обрезается при обратном присваивании; совпадает с wrap-around IEC,
  устраивает.
- Изменение переменной цикла в теле `FOR` не влияет на число итераций
  (счётчик отдельный, решение 6); по IEC так нельзя, но диагностики нет.
- Печать драйвера `-main` не разворачивает вложенные экземпляры ФБ
  (решение 4): внутреннее состояние выводится наружу явно (`=>` или
  присваивание из `inst.member`).
- Читаемость C-выхода: скобки вокруг каждой операции и явное обнуление всех
  полей в `_init` дают шумный код — осознанно, надёжность важнее.
- Присваивание в `VAR CONSTANT` не диагностируется: `sema.Symbol` не хранит
  вид блока и квалификаторы, запись в константу молча проходит.
- Раскладка `src/*` вместо Go-идиомы `internal/` + `cmd/st2c` — переезд
  отдельным механическим коммитом при появлении CI/внешних импортов.

## Рабочий стиль

- Этапы реализуются строго по одному; переход к следующему — только после
  явного «переходим дальше» от пользователя.
- Каждая законченная порция работы = отдельный коммит: `go build ./...`,
  `go vet ./...`, `go test ./...` чисто/зелено; примеры из `examples/`
  прогоняются.
- Golden-эталоны перегенерируются только осознанно, diff просматривается.
- Этот файл обновляется в том же коммите, который меняет поведение, статусы
  или список файлов.
