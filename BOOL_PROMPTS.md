# Промпты по этапам: BOOL и логические операторы

Временный файл для Mart. Открываешь новую сессию → копируешь промпт очередного
этапа → сессия выполняет этап целиком и отмечает его в `PLAN_BOOL.md`.

**Один этап = одна сессия = один коммит.** Промпты идут строго по порядку:
каждый следующий опирается на то, что предыдущий уже в коммите.

Оценка: этапы 1 и 2 — небольшие, **этап 3 (sema) — самый крупный, под него нужна
свежая сессия целиком**, этап 4 — короткий, но с обязательной регрессией
эталонов, этап 5 — средний, требует ручного счёта ожидаемых значений для
`.expected` и правки `CLAUDE.md`.

По завершении этапа 5 этот файл и `PLAN_BOOL.md` удаляются — существенное
переезжает в `CLAUDE.md`.

---

## Этап 1 — лексер и AST

```
Проект st2c, начинаем работу «BOOL и логические операторы». Прочитай CLAUDE.md и
PLAN_BOOL.md.

Выполни этап 1 из PLAN_BOOL.md целиком: семь ключевых слов (BOOL, TRUE, FALSE,
AND, OR, XOR, NOT) и токен-оператор AMP для `&` в лексере, операции AND/OR/XOR и
унарная NOT в ast.Op, узел BoolLiteral, плюс табличные тесты лексера. Все детали
и подводные камни — в PLAN_BOOL.md, раздел «Этап 1».

Главная ловушка этапа: ключевые слова попадают в tokenNames автоматически из
keywords через init(), а AMP туда надо вписать РУКАМИ — иначе String() вернёт
UNKNOWN в сообщениях парсера.

После этапа `x : BOOL;` и `a AND b` обязаны падать синтаксической ошибкой
парсера (он новых токенов ещё не знает) — это правильное промежуточное
состояние.

Рабочий стиль по CLAUDE.md: go build ./... и go vet ./... чисто, go test ./...
зелено; golden-эталоны (.ast и .c) не перегенерировать — этап 1 их менять не
должен.

По завершении отметь этап в PLAN_BOOL.md — чек-лист и журнал сессий — и
закоммить всё одним коммитом. Этап 2 не начинай.
```

## Этап 3 — sema

```
Проект st2c, работа «BOOL и логические операторы», этапы 1-2 уже в коммитах.
Прочитай CLAUDE.md и PLAN_BOOL.md.

Выполни этап 3 из PLAN_BOOL.md целиком — это ядро работы: BOOL как объявляемый
тип (builtinType, scalarOnly, returnKind), BoolLiteral и унарный NOT в выводе
типов, переписанная классификация операций в inferBinary (логические / сравнение
/ арифметика), разрешённые = и <> над BOOL при запрете порядковых сравнений,
hintOf и exprTok, поправленные формулировки сообщений, плюс новая табличная
функция TestBool и кейс в TestInfo. Все детали — в PLAN_BOOL.md, раздел
«Этап 3».

Важно по решениям плана: адаптивного булева литерала НЕТ (`b := 1;` и
`i := TRUE;` — ошибки), конверсий BOOL ↔ INT в этой работе нет, а сравнение
BOOL разрешено только через = и <> (`b1 < b2` остаётся ошибкой, теперь с
формулировкой «cannot order BOOL values»).

Codegen на этом этапе не трогаем — BOOL в C он ещё не умеет, это этап 4.

Рабочий стиль по CLAUDE.md: go build ./... и go vet ./... чисто, go test ./...
зелено; прежние тесты правятся только там, где сознательно изменилась
формулировка сообщения; golden-эталоны меняться не должны.

По завершении отметь этап в PLAN_BOOL.md — чек-лист и журнал сессий — и
закоммить всё одним коммитом. Этап 4 не начинай.
```

## Этап 4 — codegen

```
Проект st2c, работа «BOOL и логические операторы», этапы 1-3 уже в коммитах.
Прочитай CLAUDE.md и PLAN_BOOL.md.

Выполни этап 4 из PLAN_BOOL.md целиком: BOOL → _Bool в cTypes (в cWideTypes НЕ
добавлять), нули и формат печати в cZeros/cFormats, логические операции в cOps
(AND → &&, OR → ||, XOR → !=), булев литерал и унарный NOT в expr. Все детали и
обоснования (почему _Bool, почему != вместо ^) — в PLAN_BOOL.md, раздел
«Этап 4».

Важная проверка этапа: golden .c всех двенадцати существующих примеров обязаны
остаться побайтово прежними. Прогони

    set -o pipefail
    go test ./src/codegen -update && git diff --stat src/codegen/testdata

и убедись, что diff пуст. Если что-то изменилось — ошибка в правке, а не в
эталонах; восстанавливай git checkout -- src/codegen/testdata. Через пайп
(go test ... | tail) -update не запускать: провал теста не остановит цепочку и
эталоны перезапишутся неверным выводом.

После этапа прогони позитивную цепочку руками — пример из раздела «Верификация»
PLAN_BOOL.md, который компилируется gcc -std=c99 -Wall -Wextra и запускается.

Рабочий стиль по CLAUDE.md: go build ./... и go vet ./... чисто, go test ./...
зелено.

По завершении отметь этап в PLAN_BOOL.md — чек-лист и журнал сессий — и
закоммить всё одним коммитом. Этап 5 не начинай.
```
