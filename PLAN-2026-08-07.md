## Решения (приняты 2026-08-07, не переоткрывать)

Эти семь пунктов — результат обсуждения; каждый по мере реализации переезжает
в раздел «Архитектурные решения» `CLAUDE.md`.

### 1. Типы данных не расширяются — только `INT`

`VAR_INPUT` / `VAR_OUTPUT` / `VAR_IN_OUT` / `VAR_TEMP` — это **виды блоков
объявлений**, а не типы данных. Парсер разбирает всё семейство с этапа 4
доработки фронтенда, `ast.VarKind` их различает. Никакого `BOOL`, `REAL`,
`ARRAY` в этой работе нет. Счётчик, сумматор, накопитель на одном `INT` —
вполне рабочие примеры функционального блока.

### 2. PROGRAM → `typedef struct` состояния + `Name_step(Name *self)`

ПЛК работает вечным циклом: `питание → инициализация → скан → скан → …`, где
один скан = один проход тела PROGRAM. **Переменные POU живут между сканами**:
`count := count + 1;` на сотом скане даёт `count == 100`. Это не локальные
переменные функции.

Отсюда три варианта размещения переменных и выбор:

- локальные внутри функции — обнуляются на каждом вызове, семантика ПЛК
  сломана;
- глобальные / `static` — работает, но одно пространство имён на все POU и
  невозможны два экземпляра;
- **struct состояния + функция, принимающая указатель на него** — принято.

Главная выгода не в PROGRAM, а в том, что `FUNCTION_BLOCK` в IEC — это
буквально «тип с состоянием», у которого бывают экземпляры
(`inst1, inst2 : Counter;`), и каждому нужна своя память. То есть ФБ требует
ровно той же формы в C. **Один механизм на оба случая**, а не два разных.

```c
typedef struct { int16_t x; int16_t y; int16_t sum; } Example;
void Example_init(Example *self);
void Example_step(Example *self);
```

### 3. Инициализаторы VAR → отдельная `Name_init(Name *self)`

`x : INT := 5;` попадает не в C-инициализатор структуры, а в отдельную
функцию, вызываемую один раз до первого шага. Причины: работает для
неконстантных инициализаторов (свёртки констант в проекте нет), и вложенный
экземпляр ФБ рекурсивно зовёт свой `_init`:

```c
void Machine_init(Machine *self) {
    self->limit = 10;
    Counter_init(&self->cnt);
}
```

Переменные без инициализатора обнуляются явно — сгенерированный C не должен
зависеть от того, чем заполнил память вызывающий.

### 4. Флаг `-main` дописывает драйвер

Без флага генерируется библиотечный `.c`: `typedef` + функции, то, что кладут
в прошивку рядом со своим планировщиком. С флагом в конец файла добавляется
`#include <stdio.h>` и `main()`, вызывающий `_init`, затем `_step`, и печатающий
переменные состояния. Это делает файл самодостаточным для
`gcc out.c && ./a.out` — и именно этот режим дёргает сквозной тест.

### 5. Codegen в два прохода

Сначала **все** `typedef struct` и прототипы функций, потом **все** тела. ST не
требует объявлять ФБ раньше использования, C — требует. Два прохода снимают
разом и порядок POU в файле, и взаимные ссылки.

### 6. `FOR`: границы и шаг вычисляются один раз

По IEC границы цикла вычисляются **до входа** в цикл, а C-шный
`for (i = 1; i <= end; …)` пересчитывал бы `end` на каждой итерации — если в
теле цикла меняется переменная, входящая в `end`, поведение разойдётся молча.
Поэтому — временные во вложенном блоке:

```c
{
    int16_t __end = <end>;
    int16_t __step = <step>;
    for (self->i = <start>; self->i <= __end; self->i += __step) { … }
}
```

Направление: при **константном** отрицательном шаге условие сразу `>=`. При
шаге-выражении — `(__step >= 0 ? self->i <= __end : self->i >= __end)`.
Имена временных должны быть уникальны для вложенных циклов (суффикс-счётчик:
`__end0`, `__end1`, …).

### 7. Проверка codegen: golden `.c` + `gcc`

- `src/codegen/testdata/*.st` → golden `*.c`, перегенерация флагом `-update`
  (ровно как сейчас устроены `*.ast` в `src/parser`), diff смотрится руками.
- `*.expected` — ожидаемый stdout; тест собирает golden `.c` через `gcc`,
  запускает и сверяет вывод.
- Если `gcc` в системе нет — тест вызывает `t.Skip`, чтобы `go test ./...`
  оставался зелёным везде.

## Этапы

Семь этапов, **один этап = одна сессия = один коммит**. Размер каждого —
примерно 120–200 строк нового кода: этого достаточно, чтобы сессия не
разрослась и модель не начала терять принятые решения.

Границы проведены по швам «фронтенд → sema → codegen», а не по языковым
конструкциям: так каждый этап трогает один-два пакета, и его легко проверить.

### Этап 1 — каркас codegen

**Цель.** Программа из объявлений и присваиваний превращается в C, собирается
`gcc` и печатает верные значения. Заодно встают обе тестовые обвязки и CLI —
дальше они только используются.

**Контракт** (фиксируется в `CLAUDE.md`):

```go
type Options struct { Main bool }          // -main: дописать драйвер
func Generate(sf *ast.SourceFile, opts Options) (string, error)
```

Рекурсивный обход по образцу `String()` из `src/ast/ast.go` — там уже написан
хелпер `indent`, эмиттер делается по его мотивам (собственный, с уровнем
отступа и `strings.Builder`).

**Состав.**

- Пролог `#include <stdint.h>`.
- Два прохода (решение 5): для `*ast.Program` — `typedef struct` из полей всех
  `VarBlocks`, затем прототипы `Name_init` / `Name_step`; затем тела.
- `Name_init` (решение 3): присваивание инициализаторов, `0` для остальных.
- Выражения: `*ast.Identifier` → `self->x`; `*ast.IntLiteral`;
  `*ast.BinaryExpr` — **скобки вокруг каждой** операции (решение из
  `CLAUDE.md`: надёжность важнее читаемости); `*ast.UnaryExpr`.
- Таблица `ast.Op` → строка C: `EQ`→`==`, `NE`→`!=`, остальные совпадают.
- `*ast.AssignStatement`.
- CLI в `src/main.go`: флаги `-o <file>` (по умолчанию stdout), `-main`,
  `-dump-ast` (текущее поведение — печать дерева). Перевести разбор аргументов
  на пакет `flag`.

**Задел под будущие типы — обязателен.** Маппинг ST-тип → C-тип живёт в
**одной** функции `cType(typeName string) string`; литеральной строки
`int16_t` в коде codegen быть не должно нигде, кроме её таблицы. Сейчас в
таблице одна строка (`INT` → `int16_t`), потом станет десять. Это единственное
место, где нынешнее ограничение «только INT» могло бы врасти в структуру кода;
стоит ноль, экономит археологию при добавлении `BOOL`/`DINT`/`REAL`. Это же
касается временных в `FOR` (этап 2) — их тип берётся из типа переменной цикла
через `cType`, а не пишется литералом.

Строить сейчас каркас под вывод типов **не надо** — его форма пока неизвестна,
это была бы преждевременная абстракция. Требование ровно одно: не размазывать
`int16_t` по коду.

**Риск, который надо закрыть сразу.** Имя переменной или POU в ST может
совпасть с ключевым словом C (`int`, `for`, `default`, `struct`, `register`…)
или с именем из stdint. Нужен список зарезервированных слов C и
префиксование при совпадении. Если это отложить, дефект всплывёт этапа через
три и будет выглядеть как случайная ошибка `gcc`.

**Тестовая обвязка** (решение 7), ставится здесь один раз:
`src/codegen/codegen_test.go` + `src/codegen/testdata/` — golden `*.c` с флагом
`-update` по образцу `src/parser/parser_test.go`, `*.expected` и тест с `gcc`
под `t.Skip`.

**Критерий готовности.** `go run ./src -main -o /tmp/a.c <файл с
присваиваниями> && gcc /tmp/a.c -o /tmp/a && /tmp/a` печатает верные значения.
`go build ./... && go vet ./...` чисто, `go test ./...` зелено.

**`CLAUDE.md`:** статус `codegen` → «в работе»; контракт `Generate` и решения
2–5, 7 переезжают в «Архитектурные решения»; новые файлы в списке; CLI-флаги в
разделе «Команды».

**Статус:** ⬜ не начат

### Этап 3 — фронтенд POU: лексер, AST, парсер

**Цель.** `FUNCTION`, `FUNCTION_BLOCK`, вызовы функций и ФБ разбираются в
дерево. Sema и codegen не трогаются.

**Лексер** (`src/lexer/lexer.go`):

- ключевые слова `FUNCTION`, `END_FUNCTION`, `FUNCTION_BLOCK`,
  `END_FUNCTION_BLOCK` — в `keywords`, дальше `tokenNames` строится из неё
  автоматически в `init()`;
- токены `DOT` (`.`) для `inst.Out` и `ARROW` (`=>`) для `out => y`.

`readIdent` читает слово целиком, поэтому `FUNCTION_BLOCK` не спутается с
`FUNCTION` — специальной обработки не нужно. `=>` разбирается через `peek()`,
как существующие `<=` / `<>`.

**AST** (`src/ast/ast.go`), новые узлы + `String()` каждому:

- `Function{Name, ReturnType string, VarBlocks, Body, Tok}` — реализует `POU`;
- `FunctionBlock{Name string, VarBlocks, Body, Tok}` — реализует `POU`;
- `CallExpr{Callee Expression, Args []*Arg, Tok}` — реализует `Expression`;
- `Arg{Name string, Value Expression, Output bool}` — `Name == ""` для
  позиционного, `Output` для формы `name => lvalue`;
- `MemberExpr{Base Expression, Member string, Tok}` — `Expression`;
- `CallStatement{Call *CallExpr}` — `Statement`, вызов ФБ как оператор.

**Парсер** (`src/parser/parser.go`):

- ветки `lexer.FUNCTION` и `lexer.FUNCTION_BLOCK` в `switch` внутри
  `ParseSourceFile` — место под них уже размечено комментарием;
- `parseFunction`: `FUNCTION IDENT : type {VAR-блоки} {операторы} END_FUNCTION`;
- `parseFunctionBlock`: то же без типа возврата, до `END_FUNCTION_BLOCK`;
- постфиксный цикл в `parsePrimary`: после атома, пока текущий токен — `.` или
  `(`, наращивать `MemberExpr` / `CallExpr`. Это ровно тот «постфиксный
  оператор», о котором говорит раздел долгов `CLAUDE.md`;
- `parseStatement` для `IDENT`: разобрать postfix-выражение, затем по текущему
  токену решить — `:=` даёт `AssignStatement` (цель обязана быть `Identifier`
  или `MemberExpr`), `;` после `CallExpr` даёт `CallStatement`, иначе ошибка;
- `isBlockEnd` пополняется `END_FUNCTION` и `END_FUNCTION_BLOCK`.

**Тесты.** Новые `src/parser/testdata/*.st` + golden `*.ast` (функция, ФБ,
вызов с позиционными аргументами, вызов с `:=` и `=>`, `inst.Out` в выражении).
Негативные: вызов без закрывающей скобки, `=>` слева от не-lvalue.

**Временное состояние, которое надо записать явно.** `sema.Check` перебирает
`sf.POUs` и обрабатывает только `*ast.Program`, молча пропуская остальное. То
есть после этого этапа функции и ФБ **разбираются, но не проверяются**. Это
нормально и закрывается этапом 4 — но должно быть написано в `CLAUDE.md`,
иначе следующая сессия примет это за баг и полезет чинить не то.

**Критерий готовности.** Golden-эталоны новых примеров просмотрены руками,
`go test ./...` зелено, `go vet ./...` чисто.

**`CLAUDE.md`:** новые узлы AST, новые правила парсера, новые токены; в
«Известные долги» — временная слепота sema к новым POU.

**Статус:** ⬜ не начат

### Этап 4 — sema: области видимости и `FUNCTION`

**Цель.** Функции проверяются семантически. Это **единственный этап, который
меняет существующий код** — дальше снова только дописывание.

**Состав.**

- `Check` первым проходом строит глобальную таблицу POU: имя (ключ
  `strings.ToUpper`, регистронезависимость по IEC) → узел POU. Дубли имён POU —
  ошибка. Только после этого обходятся тела.
- `checker` получает ссылку на глобальную таблицу; локальная `syms` остаётся
  как есть — областей видимости внутри POU по-прежнему одна.
- `Function`: параметры берутся из блоков `VarInput`; имя функции
  регистрируется в её локальной таблице как переменная возврата с типом
  `ReturnType` (по IEC возврат — это присваивание имени функции: `Add := a + b;`).
- Проверки вызова `CallExpr`: callee объявлен; для функции — число аргументов
  совпадает с числом входов; именованные аргументы (`name := expr`) ссылаются
  на существующие входы; повторов и смеси «позиционный после именованного»
  нет; `=>` к функции неприменим.
- Запрет рекурсии (в IEC функции нерекурсивны) — прямой и взаимной, обходом
  графа вызовов.
- `FunctionBlock` на этом этапе обходится как тело со своей таблицей; вызовы
  ФБ и члены — этап 6.

**Тесты.** Table-driven по образцу существующего `src/sema/sema_test.go`: вход
→ ожидаемые подстроки ошибок с `line:col` в порядке следования либо их
отсутствие.

**Критерий готовности.** Ошибочные вызовы дают внятные сообщения с позицией;
корректная программа с функцией проходит без ошибок. `go test ./...` зелено.

**`CLAUDE.md`:** двухуровневая таблица (глобальная POU + локальная), возврат
через имя функции, список проверок; из долгов убирается «стек scope-ов придёт
с функциями».

**Статус:** ⬜ не начат

### Этап 5 — codegen `FUNCTION`

**Цель.** Пример с функцией проходит ST → C → `gcc` → запуск.

**Состав.**

- `*ast.Function` → обычная C-функция: параметры из `VAR_INPUT` как `int16_t`,
  локальные из `VAR`/`VAR_TEMP` — как локальные переменные C. Возвратная
  переменная объявляется первой строкой и возвращается последней:

```c
int16_t Add(int16_t a, int16_t b) {
    int16_t Add = 0;
    Add = (a + b);
    return Add;
}
```

  Функция состояния между вызовами не хранит — struct ей не нужен, и внутри её
  тела переменные адресуются напрямую, без `self->`. Это значит, что эмиттер
  выражений должен знать текущий контекст (POU со state или без); проще всего —
  поле в структуре генератора, устанавливаемое на входе в POU.

- `*ast.CallExpr` для функции → `Name(a, b)`; именованные аргументы
  раскладываются в позиционные по порядку `VAR_INPUT`.
- Прототипы функций — в первый проход (решение 5), поэтому порядок функций в
  ST-файле роли не играет.

**Критерий готовности.** Новый пример в `examples/` (программа + функция),
сквозной прогон через `gcc` с проверкой вывода; он же — golden-тест codegen.

**`CLAUDE.md`:** маппинг `FUNCTION` → C-функция, возврат через одноимённую
переменную, раскладка именованных аргументов.

**Статус:** ⬜ не начат

### Этап 6 — sema: экземпляры ФБ и резолв членов

**Цель.** Функциональные блоки проверяются семантически.

**Состав.**

- `inst : Counter;` — `TypeName` перестаёт быть просто строкой: если имя не
  `INT`, ищем его в глобальной таблице POU. Нашли `FunctionBlock` → символ
  становится экземпляром ФБ с ссылкой на его узел. Не нашли → ошибка
  «неизвестный тип» (сейчас пользовательские типы молча пропускаются — это
  поведение уходит).
- `MemberExpr` (`inst.Out`): база должна быть экземпляром ФБ, член ищется в его
  `VAR_INPUT` / `VAR_OUTPUT`. Отсутствующий член — ошибка с позицией.
- `CallStatement` (`inst(In := x, Out => y);`): callee — экземпляр ФБ;
  аргументы только именованные (позиционные для ФБ не поддерживаем — записать
  как решение); `name := expr` — только для `VAR_INPUT`; `name => target` —
  только для `VAR_OUTPUT`, и `target` обязан быть lvalue.
- Доступ извне: чтение `inst.Out` разрешено, запись в `inst.Out` — ошибка;
  запись `inst.In` разрешена, чтение — ошибка. (Если это покажется избыточным
  для MVP — допустимо разрешить всё, но тогда явно записать в долги.)
- ФБ не может быть типом собственного поля — проверка на циклы во вложенности
  экземпляров, иначе struct в C получится бесконечного размера.

**Критерий готовности.** Table-driven тесты на каждую из перечисленных ошибок;
корректная программа с ФБ проходит чисто.

**`CLAUDE.md`:** резолв пользовательских типов в ФБ, правила вызова ФБ,
запрет циклической вложенности.

**Статус:** ⬜ не начат

### Этап 7 — codegen `FUNCTION_BLOCK`

**Цель.** Закрытие MVP: счётчик на ФБ работает через несколько сканов.

**Состав.**

- `*ast.FunctionBlock` → `typedef struct` из всех его VAR-блоков (входы,
  выходы, внутренние — все поля одной структуры) + `Name_init(Name *self)` +
  `Name_body(Name *self)`. Форма ровно та же, что у PROGRAM (решение 2), —
  различаются только имена функций.
- Экземпляр `inst : Counter;` в POU-владельце → поле `Counter inst;` в его
  struct состояния; `Name_init` владельца рекурсивно зовёт `Counter_init(&self->inst)`
  (решение 3).
- `*ast.CallStatement` разворачивается в три части:

```c
self->inst.In = <expr>;          /* входы  := */
Counter_body(&self->inst);       /* вызов тела */
self->y = self->inst.Out;        /* выходы => */
```

- `*ast.MemberExpr` в выражении → `self->inst.Out`.
- Порядок `typedef` в первом проходе: struct владельца содержит struct
  экземпляра по значению, значит C требует, чтобы вложенный был объявлен
  раньше. Прототипы это не решают — нужна топологическая сортировка ФБ по
  вложенности. Циклы уже отсечены sema на этапе 6.

**Критерий готовности.** Пример счётчика в `examples/`: `-main`-драйвер зовёт
`_step` несколько раз подряд и печатает результат после каждого — состояние,
сохраняющееся между сканами, видно в выводе. Сквозной прогон через `gcc`.

**`CLAUDE.md`:** маппинг `FUNCTION_BLOCK` → struct + `_init`/`_body`, разворот
вызова, порядок typedef; статус всей таблицы пакетов → «готов»; MVP-раздел
переписан под новый язык; этот файл (`PLAN-2026-08-07.md`) и
`SESSIONS-2026-08-07.md` удаляются тем же коммитом.

**Статус:** ⬜ не начат

## Долги, которые копим сознательно

Записывать в «Известные долги» `CLAUDE.md` по мере появления:

- **Деление на ноль** — оставляем поведением C (UB). Проверки времени
  выполнения нет.
- **Переполнение `INT`** — `int16_t` в C промоутится до `int`, результат
  обрезается при обратном присваивании. Это совпадает с wrap-around IEC и нас
  устраивает, но зафиксировать надо.
- **Свёртка констант отсутствует** — уже в долгах; из-за неё направление `FOR`
  определяется только для литерального шага, для выражения генерится тернарник.
- **Восстановление после ошибок парсера** — по-прежнему fail-fast, отложено.
- **`VAR_IN_OUT`** — вид блока парсится, но семантики «по ссылке» у него нет;
  в MVP использовать не следует. Честная реализация — `int16_t *` в C.
- **Читаемость C-выхода** — скобки вокруг каждой бинарной операции и явное
  обнуление всех полей в `_init` дают шумный код. Решение осознанное:
  надёжность важнее.

## Что будет с масштабированием на другие типы

Вопрос задан до начала работ, ответ фиксируется здесь, чтобы не выяснять его
заново.

**Не зависит от типов вообще** (эти семь этапов останутся как есть): AST
синтаксический с типами в side-table; Pratt-парсер (новый оператор = строка в
`prec` и `binOps`); struct состояния + функция шага; `FUNCTION_BLOCK` и
вызовы; регистронезависимость; накопление ошибок в sema.

**Механическая правка вширь**: `VarDecl.TypeName string` → `TypeSpec` —
понадобится только для составных типов (`ARRAY [1..10] OF INT`, `STRUCT`,
`STRING[80]`); для скалярных (`BOOL`, `DINT`, `REAL`, `WORD`) достаточно новых
строк в таблице `cType`. Плюс `IntLiteral.Value int` → шире и новые формы
литералов в лексере (`16#FF`, `3.14`, `TRUE`/`FALSE`) — уже в долгах.

**Пишется с нуля** — слой вывода типов в sema. Сейчас его нет: `checkExpr`
протаскивает вниз строку `targetType` только ради проверки диапазона литерала,
это заглушка. Настоящий слой (тип выражения, правила продвижения, `BOOL` у
сравнений, запрет неявного смешения `INT`/`REAL` в пользу явных
`*_TO_*`-функций) по объёму сопоставим со всеми семью этапами этого плана.
Ориентировочно: `BOOL` отдельно — 2 сессии; полный слой типов — 4–5; массивы —
ещё 2.

**Существенно:** эта работа отложена, а не создана решением «пока только
`INT`». Ограничение MVP ничего не удорожает в будущем — при одном условии,
что выполнено требование про единственную точку `cType` (см. этап 1).
