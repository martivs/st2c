# 🧪 Тесты для кожаного

_Что такое тесты в Go, зачем они, и что конкретно тебе — человеку — с ними делать
после каждой подзадачи. Написано для новичка в Go._

---

## Сначала главное: кто вообще запускает тесты?

- **Во время работы тесты запускает сама модель (Fable).** У неё есть доступ к
  терминалу, она пишет тесты, гоняет их, чинит, пока не станет зелено. Это её работа.
- **Ты запускаешь тесты сам — в конце, как проверку.** Не потому что обязан, а чтобы
  своими глазами убедиться: то, что модель написала «всё зелено», — правда. Это 10
  секунд и одна команда.

Короче: модель — повар, ты — тот, кто пробует блюдо перед подачей.

---

## Что такое тест (на пальцах)

Тест — это маленькая программа, которая запускает твой код с известным входом и
проверяет, что он выдал ожидаемый результат. Если выдал не то — тест «падает»
(FAIL) и показывает, где именно.

Смысл: когда модель через неделю поменяет одну строчку и случайно что-то сломает,
тесты **сразу** об этом заорут, а не через месяц на реальной программе. Для нашего
транслятора это критично — фазы идут одна за другой и постоянно трогают лексер и
парсер.

---

## Как это устроено в Go (минимум, который надо знать)

1. **Тесты живут рядом с кодом**, в файлах с суффиксом `_test.go`. Например:
   - `src/lexer/lexer.go` — сам код
   - `src/lexer/lexer_test.go` — тесты к нему

   Эти файлы появятся в Подзадаче 1 (их сейчас нет).

2. **Одна команда запускает всё:**
   ```
   go test ./...
   ```
   `./...` означает «все пакеты в проекте, рекурсивно». Запускать из корня проекта
   (там, где лежит `go.mod`).

3. **Как читать вывод.** Хорошо выглядит так:
   ```
   ok      st2c/src/lexer    0.003s
   ok      st2c/src/parser   0.005s
   ```
   `ok` = пакет прошёл. Плохо выглядит так:
   ```
   --- FAIL: TestComments (0.00s)
       lexer_test.go:42: got PLUS, want COMMENT
   FAIL
   ```
   `FAIL` = что-то сломалось; строка ниже говорит, где (`lexer_test.go:42`) и в чём
   суть (`получили PLUS, ожидали COMMENT`).

## Три команды приёмки (запускай после КАЖДОЙ подзадачи)

Из корня проекта, по очереди:

```
go build ./...
go vet ./...
go test ./...
```

- **`go build ./...`** — «а оно вообще компилируется?». Молчание = всё хорошо.
- **`go vet ./...`** — встроенный «линтер», ловит подозрительные конструкции.
  Молчание = всё хорошо.
- **`go test ./...`** — прогоняет все тесты. Хочешь подробнее, с именами каждого
  теста — добавь `-v`:
  ```
  go test ./... -v
  ```

Если все три отработали без ошибок и без `FAIL` — подзадача действительно готова,
можно коммитить. Если хоть где-то ошибка — **не коммить**, вернись в тот же чат и
напиши модели: «`go test` падает вот с этим: <вставь вывод>, почини в рамках текущей
подзадачи».

## Что такое «golden-тесты» (у нас их много)

Наш парсер умеет печатать построенное дерево в виде текста (метод `String()`).
Golden-тест работает так:

1. Берётся эталонный входной файл — например `example.st`.
2. Парсер строит по нему дерево и печатает его в текст.
3. Этот текст сравнивается с заранее сохранённым «эталоном» (golden-файл,
   `example.ast`).
4. Совпало — тест прошёл. Не совпало — покажет построчную разницу.

«Golden» = «золотой образец». Удобно тем, что не надо руками расписывать ожидаемое
дерево — оно хранится готовым файлом.

**Важный нюанс про Подзадачу 2.** Там дерево осознанно меняется (переделывается
разбор выражений). Значит, golden-эталоны придётся **перегенерировать** — это
делается специальным флагом, обычно `-update`:
```
go test ./... -update
```
Это **нормально и предусмотрено планом**. Модель сделает это сама. Твоя проверка
здесь — не «эталоны не менялись», а «модель в отчёте подтвердила, что смысл дерева
(приоритеты операций, порядок) сохранился, изменились только подписи».

## Частые вопросы

**Мне обязательно самому запускать тесты?**
Технически нет — модель их гоняет сама. Но 10 секунд твоей проверки = уверенность,
что тебя не обманули (пусть и не со зла). Настоятельно рекомендую.

**Я запустил `go test`, а он пишет `no test files`.**
Значит, в этом пакете тестов ещё нет. До Подзадачи 1 их не будет вообще — это
ожидаемо.

**`go test` долго висит.**
У нас тесты крошечные, доли секунды. Если висит — скорее всего, ждёт ввода или что-то
пошло не так; жми `Ctrl+C` и покажи вывод модели.

**Где физически лежат тесты?**
`src/lexer/lexer_test.go`, `src/parser/parser_test.go`, а эталоны — в
`src/parser/testdata/`. Появятся в Подзадаче 1.
