# Ревью проекта st2c — ошибки, слабые места, план масштабирования

**Дата:** 2026-07-09
**Охват:** `src/lexer`, `src/parser`, `src/ast`, `src/main.go`, `src/codegen` (заглушка), `CLAUDE.md`, `examples/example.st`
**Состояние:** `go build ./...` и `go vet ./...` — чисто; `example.st` разбирается корректно.

Все ошибки из раздела 1 воспроизведены на реальных входах (тесты приведены).

## 1. Подтверждённые ошибки (воспроизведены запуском)

### 1.1. Нет комментариев ST — падение на первом же `(*`

```
PROGRAM T
(* comment *)          → line 2: unexpected token ( "(" at statement start
```

Лексер выдаёт `(*` как `LPAREN` + `STAR`. Любой реальный ST-файл содержит
комментарии `(* ... *)` (и в современных диалектах `// ...`), так что это
блокер даже для MVP. **Исправление:** в `Lexer.NextToken()` перед разбором
`(` проверять `peek() == '*'` и съедать до `*)` (учитывая вложенность —
стандарт допускает вложенные комментарии в 3-й редакции); `//` — до конца
строки. Не забывать инкрементировать `line` внутри многострочного комментария.

### 1.2. Нет унарного минуса — `x := -5;` не разбирается

```
x := -5;               → line 3: expected expression, got - "-"
```

Отрицательные константы — базовая вещь даже для «только INT».
**Исправление:** в `parsePrimary` (или отдельным уровнем `parseUnary` между
`parseMultiplicative` и `parsePrimary`) обрабатывать `MINUS` (и на будущее
`NOT`, унарный `+`) с построением узла `UnaryExpr`.

### 1.3. Нет операторов `<=`, `>=`, `<>`

```
IF x <= 3 THEN         → line 3: expected expression, got = "="
```

Лексер токенизирует `<=` как `LT` + `EQ`. Стандартный набор сравнений ST:
`= <> < > <= >=`. **Исправление:** в лексере по аналогии с `:=` — при `<`
смотреть `peek()` (`=` → `LE`, `>` → `NE`), при `>` — `=` → `GE`.

### 1.4. `FOR ... BY step` не поддержан

```
FOR i := 1 TO 10 BY 2 DO   → line 4: expected DO, got IDENT "BY"
```

`BY` — часть стандартного синтаксиса `FOR` (IEC 61131-3), а не расширение.
Пока его нет, `BY` даже не ключевое слово — лексер отдаёт его как `IDENT`,
что даёт сбивающее с толку сообщение об ошибке. **Исправление:** добавить
ключевое слово `BY`, в `ForStatement` — необязательное поле `Step Expression`
(nil → шаг 1). Важно и для codegen: направление цикла при отрицательном шаге.

### 1.5. Переполнение `INT` не диагностируется по типу

`strconv.Atoi` в `parsePrimary` отлавливает только переполнение платформенного
`int` (64 бита). IEC-тип `INT` — 16-битный (−32768..32767): литерал `100000`
сейчас молча принимается, а в сгенерированном C (`int16_t`) даст усечение.
Это задача семантического анализа (см. 3.3), но заводится она уже сейчас:
в `IntLiteral` стоит хранить и исходную строку литерала, и значение как
`int64`, а проверку диапазона делать при известном целевом типе.

## 2. Слабые места по пакетам

### 2.1. `lexer/lexer.go`

| # | Проблема | Почему важно при масштабировании |
|---|----------|----------------------------------|

| L2 | `Literal` у ключевых слов приводится к верхнему регистру, исходное написание теряется | Для сообщений об ошибках и будущего форматтера/сорсмапов лучше хранить оригинал; тип токена и так известен. |

### 2.2. `parser/parser.go`

| # | Проблема | Почему важно |
|---|----------|--------------|
| P1 | **Каскад приоритетов «одна функция на уровень» не переживёт полную грамматику выражений.** В ST уровней приоритета 11: `OR → XOR → AND → сравнения (=, <>) → отношения (<,>,<=,>=) → +,- → *,/,MOD → унарные (-, NOT) → ** → скобки/вызовы`. Это 8–9 почти одинаковых функций. | Перейти на **Pratt / precedence climbing**: одна функция `parseExpression(minPrec int)` + таблица `map[TokenType]precedence`. Новый оператор = одна строка в таблице. Это самый выгодный рефакторинг перед Этапом 4+. |
| P2 | **Цель присваивания — `string`** (`AssignStatement.Target`), в `parseFor` переменная цикла тоже `string`. | Ломается на первом же `arr[i] := ...`, `fb.output := ...`, `s.field[i+1] := ...`. Target должен быть `Expression` (lvalue): `Identifier`, позже `IndexExpr`, `MemberExpr`. Менять сейчас дёшево, после написания codegen — дорого. |
| P3 | **`VarDecl` не хранит тип** — `INT` захардкожен и в парсере (`p.expect(lexer.INT)`), и в `ast.VarDecl.String()`. | Первое же расширение типов упирается сюда. Нужно поле `Type` (для начала строка/enum, позже узел `TypeSpec` — понадобится для `ARRAY [1..10] OF INT`). Также ST допускает список имён: `a, b, c : INT;` и инициализатор `x : INT := 5;`. |
| P4 | **Единственный VAR-блок** (`Program.Vars []*VarDecl`, `if p.curIs(lexer.VAR)` — один раз). | В ST блоков может быть несколько, и разных видов: `VAR`, `VAR_INPUT`, `VAR_OUTPUT`, `VAR_IN_OUT`, `VAR_TEMP`, `VAR CONSTANT`, `VAR RETAIN`. Структура: `Vars []*VarBlock`, где `VarBlock{Kind, Decls}`; цикл `for p.curIs(VAR-семейство)`. Критично для функций и FB — у них интерфейс задаётся именно видами блоков. |
| P5 | **Корень дерева — жёстко `Program`.** `parseProgram` сразу ждёт `PROGRAM`. | Компилационная единица ST — список POU: `FUNCTION`, `FUNCTION_BLOCK`, `PROGRAM`, `TYPE ... END_TYPE`. Нужен верхний уровень `SourceFile { POUs []POU }`, а `Program` станет одним из вариантов. Лучше заложить до codegen, чтобы его вход был `*ast.SourceFile`. |
| P6 | Fail-fast: одна ошибка на запуск. | Для MVP осознанно и нормально, но при росте файлов пользователь будет чинить ошибки по одной. План: режим восстановления — при ошибке в statement скатываться до ближайшего `;` / `END_*` (synchronize) и копить `[]error`. Текущая архитектура с полем `err` расширяется до `errs []error` безболезненно. |
| P7 | Нет `ELSIF`, `WHILE`, `REPEAT ... UNTIL`, `CASE`, `EXIT`, `CONTINUE`, `RETURN`. | Ожидаемо для MVP — фиксирую как обязательный список Этапа 4; `parseStatement`-диспетчер и `isBlockEnd` расширяются прямолинейно (в `isBlockEnd` добавятся `ELSIF`, `END_WHILE`, `END_REPEAT`, `UNTIL`, `END_CASE`). |
| P8 | `a < b < c` разбирается (левоассоциативно) без предупреждения. | В ST сравнения возвращают BOOL; `(a<b) < c` — сравнение BOOL с INT, должно отлавливаться на этапе семантики (см. 3.3). Пока просто зафиксировать в тестах. |
| P9 | Вызовы функций в выражениях (`f(x, y)`) и обращения к FB (`fb(in := 1); y := fb.out;`) не заложены в `parsePrimary`. | Появятся вместе с функциями. При Pratt-парсере `(` после primary — это постфиксный оператор вызова; удобно ложится в ту же таблицу. |

### 2.5. Семантическая дыра, общая для всех пакетов

Сейчас **никто не проверяет объявленность и согласованность переменных**:

- `x := undeclared;` — разбирается молча (подтверждено запуском);
- `Sum` и `sum` считаются разными именами, хотя **идентификаторы в IEC 61131-3
  регистронезависимы** — как и ключевые слова. Лексер это учитывает для
  ключевых слов, но для `IDENT` сохраняет регистр, и сравнение строк в
  дальнейшем будет чувствительным. Программа `VAR Sum : INT; END_VAR sum := 1;`
  сейчас проходит парсер и на этапе codegen даст C-код с необъявленной
  переменной `sum`;
- переменная цикла `FOR i := ...` не проверяется на объявленность;
- дубликаты объявлений (`x : INT; x : INT;`) не отлавливаются.

Парсер и не должен это делать — но тогда это должен делать кто-то между
парсером и codegen. Если засунуть проверки в codegen, они там и останутся,
и с ростом типов codegen превратится в кашу.

## 3. Рекомендуемое решение (с прицелом на типы, функции, FB)

### 3.1. Порядок работ

Ключевая мысль: **перед Этапом 3 (codegen) дешевле всего исправить формы
данных, на которые codegen завяжется** — Target-как-Expression (P2), тип в
VarDecl (P3), VAR-блоки (P4), API codegen (M2). Всё остальное можно делать
после.

1. **Этап 2.5 — закрытие долгов парсера/лексера** (до codegen):
   - комментарии `(* *)` и `//` (1.1);
   - `<=`, `>=`, `<>` (1.3); унарный минус/`UnaryExpr` (1.2); `BY` (1.4);
   - `AssignStatement.Target Expression` (P2);
   - `VarDecl.Type` + список имён + `VarBlock{Kind}` (P3, P4);
   - тесты: лексер table-driven, парсер golden (M1).
2. **Этап 3 — codegen для INT**, вход `*ast.Program`, выход C-строка (M2, M3).
   Здесь же решается маппинг `INT → int16_t` (`#include <stdint.h>`),
   `=` → `==`, `<>` → `!=`, и стратегия скобок (проще и надёжнее — скобки
   вокруг каждого BinaryExpr, читаемость C-выхода вторична).
3. **Этап 3.5 — пакет `sema`** (символьная таблица + проверки из 2.5):
   `Check(prog) []error` между парсером и codegen. Символьная таблица —
   `map[string]*Symbol` с ключом `strings.ToUpper(name)` (регистронезависимость),
   пока один уровень области видимости; с приходом функций — стек scope-ов.
4. **Этап 4 — типы**: имена типов перестают быть ключевыми словами (L5),
   `TypeSpec` в AST, вывод типов выражений в `sema` (side-table, A4),
   правила неявных преобразований IEC (или, проще и безопаснее для
   транспилятора, — явные `*_TO_*` функции и запрет неявных смешений).
5. **Этап 5 — операторы** `ELSIF/WHILE/REPEAT/CASE/EXIT/RETURN` (P7) +
   Pratt-переход в выражениях (P1) + восстановление после ошибок (P6).
6. **Этап 6 — POU**: `SourceFile` как корень (P5), `FUNCTION` /
   `FUNCTION_BLOCK` / `VAR_INPUT|OUTPUT|IN_OUT`. Маппинг на C, который
   стоит зафиксировать заранее:
   - `FUNCTION` → обычная C-функция;
   - `FUNCTION_BLOCK` → `struct` (состояние = VAR + VAR_OUTPUT) + функция
     `void FB_Name(FB_State *self, inputs...)` — стандартный приём, ложится
     на семантику FB «экземпляр с памятью» один в один;
   - `PROGRAM` → struct-состояние + функция шага (готовит почву для задач/
     циклического исполнения PLC).

### 3.2. Что менять в первую очередь в коде (конкретика)

- `lexer`: `readComment()`, двухсимвольные `<= >= <>` в `switch` (по образцу
  `:=`), `Col` в `Token`, ключевые слова `BY`, `WHILE`, `ELSIF`, … по мере
  надобности; таблицу `tokenNames` для ключевых слов строить из `keywords`
  в `init()` — исчезнет тройное дублирование (L3, и TODO на строке 100).
- `ast`: `UnaryExpr`; `AssignStatement{Target Expression}`;
  `VarBlock{Kind VarKind, Decls []*VarDecl}`; `VarDecl{Names []string,
  Type string, Init Expression}`.
- `parser`: `parseUnary`; `parseVarBlocks` (цикл по блокам);
  `parseFor` — опциональный `BY`; `parseAssign` начинает с
  `parsePrimary`-lvalue вместо голого `IDENT`.
- `codegen`: зафиксировать `Generate(*ast.Program) (string, error)`,
  рекурсивный обход по образцу `String()`.
- Тесты: `lexer/lexer_test.go`, `parser/parser_test.go` + `testdata/*.st`
  с golden-файлами.

### 3.3. Чего *не* делать сейчас

- Не переходить на Pratt немедленно: текущий каскад корректен и покрыт
  малым числом уровней; переход осмыслен вместе с добавлением
  `AND/OR/XOR/MOD/**` (Этап 5), одним коммитом с тестами.
- Не строить полноценную систему типов до рабочего codegen для INT —
  иначе Этап 3 никогда не закончится.
- Не менять раскладку каталогов (M4) одновременно с функциональными
  правками — отдельным механическим коммитом, если вообще менять.
