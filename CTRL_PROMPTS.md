# Промпты по этапам: ELSIF / WHILE / REPEAT / EXIT

Временный файл для Mart. Открываешь новую сессию → копируешь промпт очередного
этапа → сессия выполняет этап целиком и отмечает его в `PLAN_CTRL.md`.

**Один этап = одна сессия = один коммит.** Промпты идут строго по порядку:
каждый следующий опирается на то, что предыдущий уже в коммите.

Разбивка — **по слоям**: сессия 1 делает лексер и AST сразу для всех четырёх
конструкций, сессия 2 — парсер для всех четырёх, сессия 3 — sema и codegen,
сессия 4 — эталоны и документацию. Пример `ctrl_all` написан заранее, в
коммите плана.

Оценка: ревью плана — необязательное, до этапа 1; этап 1 — небольшой (с
одной ожидаемой правкой старого теста лексера); этап 2 — средний, много
структурных и негативных тестов, плюс важная заглушка в codegen и
переименование примера; **этап 3 — самый содержательный** (sema + codegen в
одной сессии, приёмка — заранее написанный пример `ctrl_all`), но короче, чем
sema у BOOL; этап 4 — короткий: эталоны для готового примера и правка
`CLAUDE.md`.

По завершении этапа 4 этот файл и `PLAN_CTRL.md` удаляются — существенное
переезжает в `CLAUDE.md`.

---

## Ревью плана (необязательно, до этапа 1)

Так делали с планом 2026-08-07: три раунда правок (0.0.31–0.0.33) до первой
строки кода, ревью нашло бесконечный `FOR` на границе `INT` и коллизии
служебных имён. Свежая сессия не знает обсуждения и читает план так, как его
прочтут сессии этапов, — поэтому видит дыры, которые автор не видит.

```
Проект st2c. Прочитай CLAUDE.md, PLAN_CTRL.md, CTRL_PROMPTS.md и код в src/.
Код НЕ меняй — это ревью плана работы «операторы ELSIF / WHILE / REPEAT /
EXIT» до начала реализации.

Проверь план против реального кода: верны ли ссылки на файлы и строки; не
пропущено ли место, которое придётся править (особенно ветки switch по типам
узлов в sema и codegen и всё, что перебирает операторы); честны ли
промежуточные состояния (нет ли этапа, после которого получается молча
неверный C); хватает ли тестов; нет ли противоречий с решениями CLAUDE.md.

Проверь пример examples/ctrl_all.st.draft: пересчитай вручную ожидания из
его шапки; найди конструкцию, которую он не покрывает, хотя план обещает.

Решения 1-7 плана не переоткрывай — только если найдёшь, что какое-то из
них ломается о код; тогда опиши, как именно.

Результат — список находок по важности, с предложенной правкой плана для
каждой. Сам план не правь: правки внесёт Mart или следующая сессия.
```

## Этап 1 — лексер и AST

```
Проект st2c, начинаем работу «операторы ELSIF / WHILE / REPEAT / EXIT».
Прочитай CLAUDE.md и PLAN_CTRL.md.

Выполни этап 1 из PLAN_CTRL.md целиком: семь ключевых слов (ELSIF, WHILE,
END_WHILE, REPEAT, UNTIL, END_REPEAT, EXIT) в лексере; в AST — ElsIfClause,
поле ElsIfs у IfStatement, узлы WhileStatement, RepeatStatement,
ExitStatement с методами String() в формате из плана; табличные тесты
лексера. Все детали — в PLAN_CTRL.md, раздел «Этап 1».

Две вещи, на которые обрати внимание:
1. В String() у IfStatement блок «ElsIf:» печатается ТОЛЬКО для непустого
   списка — иначе на этапе 2 разъедутся все golden .ast с IF.
2. Кейс «number rollbacks» в TestAllTokens ожидает `1EXIT` как INT_LIT +
   IDENT. После этапа EXIT — ключевое слово, ожидание меняется на
   INT_LIT + EXIT. Это ожидаемая правка, не регрессия, и единственный
   прежний тест, который трогается в этой работе.

После этапа `WHILE x DO` обязан падать синтаксической ошибкой парсера (он
новых токенов ещё не знает) — это правильное промежуточное состояние.
examples/ctrl_all.st.draft не трогать — он переименовывается на этапе 2.

Рабочий стиль по CLAUDE.md: go build ./... и go vet ./... чисто, go test ./...
зелено; golden-эталоны (.ast и .c) не перегенерировать — этап 1 их менять не
должен.

По завершении отметь этап в PLAN_CTRL.md — чек-лист и журнал сессий — и
закоммить всё одним коммитом 0.2.24. Этап 2 не начинай.
```

## Этап 2 — парсер

```
Проект st2c, работа «операторы ELSIF / WHILE / REPEAT / EXIT», этап 1 уже в
коммите. Прочитай CLAUDE.md и PLAN_CTRL.md.

Выполни этап 2 из PLAN_CTRL.md целиком: ветки WHILE/REPEAT/EXIT в
parseStatement, новые терминаторы в isBlockEnd (ELSIF, END_WHILE, UNTIL,
END_REPEAT), цикл по ELSIF в parseIf, правила parseWhile, parseRepeat,
parseExit; структурные тесты (новая функция TestControl) и негативные в
TestParseErrors по таблице из плана. Все детали — в PLAN_CTRL.md, раздел
«Этап 2».

Обязательно на этом же этапе — временная заглушка в codegen: ветка
IfStatement возвращает ошибку «ELSIF is not supported yet», если ElsIfs не
пуст. Без неё codegen молча выбросит ветки ELSIF и выдаст неверный C. Этап 3
её удалит.

После `UNTIL выражение` точка с запятой НЕ ставится (по IEC):
`UNTIL a; END_REPEAT` — ошибка. После END_WHILE / END_REPEAT `;`
необязательна, как после END_IF.

Тем же коммитом: git mv examples/ctrl_all.st.draft examples/ctrl_all.st.
Пример написан до кода и является заданием — текст не менять. После этапа
он обязан разбираться (go run ./src -dump-ast examples/ctrl_all.st) и
проходить TestExamplesClean, а генерация C — падать внятной ошибкой.
Эталон .ast для него не создавать — это этап 4.

Обязательная проверка этапа: девять существующих golden .ast должны
совпасть побайтово. Прогони

    go test ./src/parser && git diff --stat src/parser/testdata

и убедись, что diff пуст. Если разъехалось — «ElsIf:» печатается при пустом
списке; -update не запускать.

Рабочий стиль по CLAUDE.md: go build ./... и go vet ./... чисто, go test ./...
зелено.

По завершении отметь этап в PLAN_CTRL.md — чек-лист и журнал сессий — и
закоммить всё одним коммитом 0.2.25. Этап 3 не начинай.
```

## Этап 3 — sema и codegen

```
Проект st2c, работа «операторы ELSIF / WHILE / REPEAT / EXIT», этапы 1-2 уже
в коммитах. Прочитай CLAUDE.md и PLAN_CTRL.md.

Выполни этап 3 из PLAN_CTRL.md целиком.

Sema: общий хелпер checkCondition(kw, e) для IF / ELSIF / WHILE / UNTIL
(сообщение для IF остаётся побайтово прежним); обход веток ELSIF и тел
циклов; счётчик циклов loops в checker и ошибка «EXIT outside of a loop».
Порядок проверок — как в исходнике (у REPEAT сначала тело, потом UNTIL).
Новая табличная функция TestControl по списку из плана.

Codegen: удалить заглушку этапа 2; IF с ELSIF → цепочка `} else if (…) {`;
WHILE → `while (c) {…}`; REPEAT → `do {…} while (!(c));` (отрицание
обязательно — UNTIL означает «повторять, пока НЕ»); EXIT → `break;` плюс
внутренняя защита «EXIT outside of a loop (sema must reject this)» и кейс в
TestNameErrors со skipSema.

Важно по решению 7 плана: goto в сгенерированном C не используется никогда.
Оставь у ветки EXIT комментарий с этим инвариантом: switch и служебные
циклы-обёртки не эмитятся; если появятся (будущий CASE) — EXIT внутри них
передаётся через флаг __exitN. Сам флаг в этой работе не реализуется.

Все детали — в PLAN_CTRL.md, раздел «Этап 3».

Регрессия этапа: golden .c всех тринадцати существующих примеров обязаны
остаться побайтово прежними:

    set -o pipefail
    go test ./src/codegen -update && git diff --stat src/codegen/testdata

diff должен быть пуст. Если что-то изменилось — ошибка в правке, а не в
эталонах; восстанавливай git checkout -- src/codegen/testdata. Через пайп
(go test ... | tail) -update не запускать.

Приёмка этапа — пример examples/ctrl_all.st, написанный до кода: собери его
с -main -scans 3, скомпилируй gcc -std=c99 -Wall -Wextra и сверь вывод с
ожиданием в шапке примера, построчно. Если не сошлось — сначала ищи ошибку в
реализации (таблица «шесть типичных ошибок» в PLAN_CTRL.md подскажет, где);
пример правь, только если ошибка в его расчёте, и запиши это в журнал.
Эталоны .c/.expected для него не создавать — это этап 4.

Плюс позитивная цепочка и негативы из раздела «Верификация» PLAN_CTRL.md
(короткий позитив обязан напечатать n=4 k=3 m=2).

Рабочий стиль по CLAUDE.md: go build ./... и go vet ./... чисто, go test ./...
зелено; прежние тесты не правятся.

По завершении отметь этап в PLAN_CTRL.md — чек-лист и журнал сессий — и
закоммить всё одним коммитом 0.2.26. Этап 4 не начинай.
```
